The answer framework

The same 7 moves solve almost any question. Go in order, say each step out loud, and always finish on trade-offs.

  1. Clarify requirementsFunctional features + non-functional targets: scale, latency, availability, consistency. Ask, don't assume.
  2. EstimateBack-of-the-envelope: QPS, reads/writes, storage, bandwidth. It justifies every later choice.
  3. Define the APIThe core endpoints / contracts — pins down exactly what the system must do.
  4. Data modelEntities and storage choice — SQL vs NoSQL, and why. Sketch the key schema.
  5. High-level designDraw the boxes: client → load balancer → services → DB / cache / queue.
  6. Deep divePick 1–2 components and go deep: sharding, replication, caching, indexing, hot keys.
  7. Bottlenecks & trade-offsSingle points of failure, back-pressure, monitoring — and the CAP trade-off you chose.

Step 5 — the boxes you almost always draw

Numbers to know

Memorize these orders of magnitude — they make your Step 2 estimates instant and credible.

L1 cache reference0.5 ns
Main memory reference100 ns
Read 4 KB from SSD150 µs
Round trip in same datacenter0.5 ms
Read 1 MB sequentially · memory0.25 ms
Read 1 MB sequentially · SSD1 ms
Disk seek10 ms
Read 1 MB sequentially · disk~20 ms
Round trip India ↔ US~250 ms

Rule of thumb: memory is ~100× faster than SSD, SSD ~20× faster than disk, and anything crossing regions costs tens–hundreds of ms.
