Consistent Hashing

When data is spread over many machines, something has to decide which machine owns which key, and keep that answer stable when machines come and go. These notes follow the lesson from plain hash-based routing to the ring, then go deeper on virtual nodes, replication, hot keys and the questions interviewers ask next.

26 min 27 s video Blue sections · from the video Amber sections · extra depth

The whole lesson in six lines

  1. Consistent hashing answers exactly one question: “which node owns this key?” It is a function call inside your proxy or load balancer, not a service, and it moves no data by itself.
  2. The usual way to pick an owner is hash(key) % N. For stateless API servers that is fine: when N changes, any server can still handle any request.
  3. For stateful nodes, such as a distributed key-value store, it breaks. Change N and most keys are suddenly “owned” by a different node, so you must move them all before you can serve again.
  4. Consistent hashing drops the “% N”. Hash the nodes and the keys onto the same number range, bend it into a ring. A key belongs to the first node clockwise from it.
  5. Add a node and it takes keys only from the node just clockwise of it. Remove a node and its keys go only to that neighbour. Everyone else is untouched, so the operation is: snapshot one node, copy, delete the extras.
  6. The implementation is a sorted array of node positions plus a binary search. The lesson insists you build it yourself; the lab does.

1

Ownership, and routing by hash

From the video▶ 0:00

The lesson starts by clearing up misconceptions. Consistent hashing is not a magical solution and it is not a service. It is an algorithm that answers one question: who owns this? Which node holds this key, which server handles this request, which machine manages this partition. Ownership, and nothing else.

Hash-based routing ▶ 1:46

Take a load balancer with three servers behind it. A request arrives; the load balancer must pick a server. One common way is hash-based routing: take something from the request (the user ID, the IP address, a request ID), hash it, and take the result mod 3. You get 0, 1 or 2. Send the request to that server.

The hash function can be anything: SHA-256, SHA-1, MD5. It turns the user ID into a big number; the mod turns the big number into a server index.

It is a function, not a service ▶ 3:02

The routing logic lives inside the load balancer’s request handler. It does not call out to another microservice. “We just don’t add random microservices for the sake of it. This is how real systems are built.” Keep that sentence; the lesson repeats it for consistent hashing too.

2

Stateless servers: changing N costs nothing

From the video▶ 4:01

Now say traffic has dropped and you want to remove one of the three servers. The load balancer changes mod 3 to mod 2. The next request for user 42 may land on a different server than before. Is that a problem?

No. Because the API servers are stateless. None of them keeps anything about user 42 between requests. Every server is equally capable of handling any request. So it does not matter which one a request goes to, and removing a server causes no hiccup at all.

This is why hash-based routing (and round robin) is so common for the load-balancer-plus-API-servers layer. Statelessness makes “which server” an unimportant question.

3

Stateful nodes: the same trick breaks

From the video▶ 6:25

Replace the API servers with storage nodes: a distributed key-value store. “Store this key with this value”, “give me the value for this key”. The data is split across the nodes; there is no single database that has everything. In front of them sits a proxy that decides, for each key, which node to talk to.

The proxy does the same thing as before: hash(key) % 3. The key is stored on the node the hash points to. Because the hash of a key never changes, every later request for that key goes to the same node. That node owns the key.

Now remove a node ▶ 9:15

Just like before, remove node 2. The proxy switches to mod 2. But now you cannot simply send “get k3” wherever the new function says, because the data for k3 is only on the node that owned it under the old function. The output of the hash function did not change; the mod did, and with it the ownership of almost everything.

So before node 2 can go, you must go through every key, recompute hash(key) % 2, and move each key that now belongs somewhere else. The lesson’s six keys:

KeyOwner with mod 3Owner with mod 2Must move?
k1node 2node 0yes
k2node 0node 1yes
k3node 1node 1no
k4node 2node 0yes
k5node 1node 1no
k6node 0node 0no

Three of six keys moved: 50%. Notice that keys like k2 moved between two nodes that are both staying. With millions or billions of keys this is a huge data transfer, and you cannot serve the new layout until it is finished. The lesson calls this repartitioning, and it is the limitation of hash-based routing: you handed your power to a hash function, and when the function changes the mapping changes with it.

The question that leads to consistent hashing ▶ 12:32

Can we minimise data movement when a node is added or removed? Twelve minutes of the video exist to make you feel this problem before seeing the answer.

4

Consistent hashing: the ring

From the video▶ 12:45

Like hash-based routing, consistent hashing answers “who owns this key”. What it does not do: it will not transfer data for you, and it is not a service. It is a function. You give it a key and the current list of nodes, and it tells you the owner. The moving of data is still your job.

Build the ring ▶ 13:47

Take the same hash function as before, but without the mod. A hash function like SHA-1 gives a number between 0 and 2¹²⁸−1 (the lesson says 128 bits; the exact width does not matter). Imagine that whole range laid out and bent into a circle, so that the maximum value is followed by 0 again. That circle is the hash ring. The lesson uses a toy range of 0 to 15 so you can see it.

Now every storage node takes a slot on the ring: hash something that identifies the node (its IP address, its name) and that number is its position. In the lesson, node 0 lands on slot 3, node 2 on slot 8, node 1 on slot 12.

Find the owner ▶ 17:24

To find who owns key k1, hash k1 with the same function. Say it gives 0. Place it on the ring at 0, then walk clockwise until you hit a node. The first node you meet owns the key. From 0 the first node is at 3: node 0 owns k1. Key k2 hashes to 10; walking clockwise the first node is at 12: node 1 owns k2.

5

Scaling up and down with minimal movement

From the video▶ 18:37

Add a node

The three-node cluster is not enough, so you add node 3. Hash its address; say it lands on slot 1. Which keys are affected? Only the keys that hash to the stretch of ring between the previous node (node 1 at 12) and the new node at 1, that is slots 13, 14, 15, 0 and 1. Those keys used to walk clockwise to node 0; now they stop at node 3 first.

Every other key is untouched. Keys between 1 and 3 still go to node 0. Keys between 3 and 8 still go to node 2. Keys between 8 and 12 still go to node 1. Only one stretch of the ring changed owner, and you know exactly which one.

How you actually do it ▶ 20:27

Do you have to scan all the keys to find the affected ones? No. Every affected key currently lives on one node: the one just clockwise of the new slot (node 0). So:

  1. Snapshot node 0

    Take a copy of the node that is about to give up keys. It is the only node involved.

  2. Create node 3 from the snapshot

    Start the new node with that copy of the data. It now has more than it needs.

  3. Add node 3 to the ring and start serving

    Insert its position into the sorted array in the proxy. From now on keys in 13 … 1 are routed to node 3, which has them.

  4. Delete the extras

    On node 3, delete the keys that do not hash into 13 … 1. On node 0, delete the keys that do. Both deletes can run in the background.

You never touched node 1 or node 2. Snapshot, spin up, add, clean up. “That is the beauty of this algorithm: simple to understand and simple to operate.”

Remove a node ▶ 22:10

Scaling down is the mirror image. Say you remove node 0. Its keys walk clockwise and now stop at the next node, node 2. So: dump everything from node 0, load it into node 2, remove node 0 from the array. Node 2 takes a little more traffic, which is fine, since you are scaling down because you were over-provisioned. Again, nobody else is involved, and you do not even need to look at individual keys: you copy the whole node.

The property in one line

Adding or removing a node changes the owner of only the keys on one stretch of the ring, and those keys all live on one neighbour. That is “consistent”: the mapping stays mostly the same when N changes.

6

A function, not a service: implement it

From the video▶ 23:37

The lesson ends with homework and a point of view. The homework: watch again until the idea is solid, then read the author’s 2020 blog post (arpitbhayani.me, “consistent hashing”), which has a Python implementation, and implement it in your own language. It needs one sorted array and one binary search. The lesson says two arrays is already overkill.

The point of view: drawing rings is visually appealing and makes the idea easy, but “the real fun is you will have to implement it someday.” System design is not theory. At every stage, think about how the thing would actually be built. Consistent hashing is the perfect example: it sounds like infrastructure, and it is twenty lines of code inside the proxy.

7

Going deeper

Extra depth · not in the video

The lesson gives you the ring with one point per node. Real systems add a few things on top, and these are what the follow-up questions are about.

7.1 · One point per node gives an uneven ring

Hash three node names and you get three random positions. Random positions make random gaps: one node may own half the ring while another owns a tenth. The lab below measures it: with 10,000 keys and 3 nodes, one node got 53% of the keys and another 19%. Add a node and it only relieves its one neighbour, so a hot node stays hot unless the new node happens to land just before it.

The fix is virtual nodes (vnodes). Instead of one position per physical node, give each node 100 to 200 positions, by hashing node-1#0, node-1#1, and so on. The ring is now cut into hundreds of small stretches, spread around, and each physical node owns a sample of them. The large-number effect evens things out:

Points per nodeKeys on S1 · S2 · S3 (of 10,000)Keys moved when S4 is addedKeys moved when S2 is removed
12,781 · 5,310 · 1,909846 (8%, too few: S4 landed in a small gap)5,310 (53%): all of S2’s keys to one neighbour
1503,792 · 3,045 · 3,1632,588 (26%, close to the ideal ¼)2,357 (24%), spread over S1, S3 and S4

Virtual nodes buy three things: even load; when a node dies its keys spread over all the others instead of landing on one neighbour; and weighting, since a machine with twice the capacity can simply get twice the points. Cassandra calls them tokens; it started with 256 per node and moved to 16 with a smarter allocation.

7.2 · How much moves, in numbers

Changehash(key) % NConsistent hashing
3 → 4 nodes~75% of keys move~25% move (1/4), all from one node
10 → 11 nodes~91% move~9% move (1/11)
100 → 101 nodes~99% move~1% move (1/101)
Remove 1 of Nalmost everythingexactly that node’s keys: 1/N

1/(N+1) is the theoretical minimum: the new node must take its fair share from somewhere. Consistent hashing moves nothing beyond that minimum. Modulo moves nearly everything, and most of it between nodes that are not even changing.

7.3 · Replication on the ring

The lesson stores each key once. Real stores keep R copies (usually 3) so a dead node loses no data (lesson 19). The ring gives a natural rule: a key is stored on the first R distinct physical nodes you meet walking clockwise. Amazon’s Dynamo paper calls this list the preference list; Cassandra, Riak and ScyllaDB work the same way. “Distinct physical” matters once you have virtual nodes: two consecutive points may belong to the same machine, and a copy on the same machine is not a copy.

7.4 · Hot keys: the ring balances keys, not traffic

Consistent hashing spreads keys evenly. It knows nothing about how often each key is read. One celebrity’s profile, one viral post, one tenant’s huge table all hash to a single point, so one node takes the whole load. This is the hot key (or hot partition) problem, and no hashing scheme fixes it by itself.

  • Cache in front: a hot key is by definition read a lot, so a cache absorbs it (lesson 19’s picture, cache box).
  • Split the key: write post:99#1 … post:99#8 to eight places; read from one at random (for counters, add them up).
  • Bounded loads: a variant (Google, 2017) that caps each node at, say, 125% of average and spills extra keys to the next node clockwise. Vimeo uses it for video routing.

7.5 · Who holds the ring, and how it stays in sync

The sorted array lives in whoever routes: the proxy, or a client library inside every API server (Memcached and Cassandra clients work this way; there is no proxy at all). That raises a question the lesson skips: all of those copies must agree on the membership list, or two clients send the same key to different nodes.

  • Gossip: nodes tell each other who is alive; clients ask any node for the current ring. Cassandra and Dynamo do this.
  • A coordination service: the member list lives in ZooKeeper or etcd and clients watch it for changes. This is lesson 20’s box doing another job.
  • Version the ring: a request carries the ring version it used; a node that receives a key it no longer owns answers “moved, here is the new owner” instead of serving stale data.

7.6 · The alternatives you should be able to name

ApproachHow it worksWhen it is the better pick
Fixed hash slots (Redis Cluster)Always hash % 16384, then a small table mapping each slot to a node. Moving a node means editing the table, not rehashing keys.Same benefit as the ring, simpler to reason about, and slots can be moved one at a time while serving. The most common “real” answer today.
Rendezvous (HRW) hashingFor a key, compute hash(key, node) for every node and pick the highest. No ring, no array, perfectly even.Few nodes (tens), and you want no data structure to keep in sync. Removing a node moves only its keys.
Jump consistent hashA tiny arithmetic function from (key, N) to a bucket in 0 … N−1 with minimal movement. No memory at all.Buckets are numbered and only ever added or removed at the end.
Range partitioningSplit keys by sorted ranges (A–F, G–M, …) and keep a directory of which node has which range. HBase, Bigtable, Spanner, MongoDB ranged sharding.You need range scans (“all orders from March”). Hashing destroys order; ranges keep it. The price: hot ranges and a directory service.

7.7 · Where you have already met it

SystemWhat the ring decides
Dynamo, Cassandra, Riak, ScyllaDBWhich nodes store each row, with virtual nodes (tokens) and the next-R-clockwise replication above. The 2007 Dynamo paper is where most engineers first met the idea.
Memcached client libraries (ketama)Which cache server holds a key. Adding a cache server used to empty every cache (modulo); the ring made it cheap. Nginx and Envoy’s “consistent hash” load balancing is the same library idea.
Akamai’s CDNWhich edge cache serves a URL. Consistent hashing was invented for this, in a 1997 paper by Karger and others, before it was used for databases.
DiscordWhich server process holds a guild’s live session, so all messages for one community land on one machine.
Chord and other DHTsPeer-to-peer lookup: every node is a point on a ring and holds a few shortcuts to find any key in log N hops.

7.8 · Limits worth saying out loud

  • It moves no data. It tells you what must move. The copy, the cut-over and the clean-up are your system’s job, and they take bandwidth and time while serving traffic.
  • The snapshot trick needs a store that can snapshot. And during the copy, writes to the moving stretch must be sent to both nodes or replayed afterwards.
  • No range queries. Hashing scatters neighbouring keys across the ring on purpose. If you need “all keys between X and Y”, use range partitioning.
  • Even keys, not even load. Virtual nodes fix the gaps; they do not fix a hot key.
8

Hands-on lab

Exercise from the video▶ 23:37 · code added here

The lesson’s exercise is to implement consistent hashing yourself, with one sorted array and a binary search. Below is one version in Python. It also measures the three claims from the notes: modulo moves most keys, the plain ring is uneven, and virtual nodes fix it.

  1. Save this as ring.py

    The whole algorithm is the Ring class: a sorted list of (position, node) and one bisect call. The rest is measurement.

    import bisect, hashlib
from collections import Counter

def h(s):
    # any hash works; we take 32 bits so the ring is 0 .. 2^32-1
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:4], "big")

class Ring:
    def __init__(self, vnodes=1):
        self.vnodes = vnodes
        self.points = []          # sorted list of (position, node)  <- this IS the ring

    def add(self, node):
        for i in range(self.vnodes):
            bisect.insort(self.points, (h(f"{node}#{i}"), node))

    def remove(self, node):
        self.points = [p for p in self.points if p[1] != node]

    def owner(self, key):
        # first point clockwise of the key; wrap around to the start at the end of the ring
        i = bisect.bisect_right(self.points, (h(key), chr(255)))
        return self.points[i % len(self.points)][1]

keys = [f"user:{i}" for i in range(10_000)]

def report(title, before, after):
    moved = sum(before[k] != after[k] for k in keys)
    print(f"{title:<42} keys moved: {moved:>5}  ({moved / len(keys):.0%})")

# 1. plain modulo: hash(key) % N
mod3 = {k: f"S{h(k) % 3 + 1}" for k in keys}
mod4 = {k: f"S{h(k) % 4 + 1}" for k in keys}
report("modulo, 3 -> 4 servers", mod3, mod4)

# 2. the ring, first with one point per server, then with 150
for v in (1, 150):
    ring = Ring(vnodes=v)
    for n in ("S1", "S2", "S3"):
        ring.add(n)
    with3 = {k: ring.owner(k) for k in keys}
    print(f"\nring with {v} point(s) per server, 3 servers -> keys per server:",
          dict(sorted(Counter(with3.values()).items())))
    ring.add("S4")
    with4 = {k: ring.owner(k) for k in keys}
    report(f"ring ({v} vnodes), add S4", with3, with4)
    ring.remove("S2")
    without2 = {k: ring.owner(k) for k in keys}
    report(f"ring ({v} vnodes), then remove S2", with4, without2)
  2. Run it 
    python3 ring.py
    modulo, 3 -> 4 servers                     keys moved:  7391  (74%)

ring (1 vnodes), add S4                    keys moved:   846  (8%)

ring (150 vnodes), add S4                  keys moved:  2588  (26%)
ring (150 vnodes), then remove S2          keys moved:  2357  (24%)
  3. Read the numbers

    Modulo moved 74% of keys going from 3 to 4 servers, as the table in 7.2 predicted. The plain ring was lopsided (S2 held 53%) and adding S4 relieved only the small gap it landed in. With 150 points per server the split is within 10% of even, adding S4 moved 26% (ideal: 25%), and removing S2 moved exactly S2’s keys and spread them over the other three.

  4. Notice what is faked

    The script only computes who owns what. It moves no data. That is precisely the lesson’s point: consistent hashing is this function; the copying in section 5 is a separate job for your storage layer.

Try next

Give S1 twice the points of the others and check it gets about twice the keys (weighting). Add owners(key, r=3) that returns the next three distinct nodes clockwise (section 7.3). Then print, for the add-S4 case, which node each moved key came from: with one point per server it is always one node; with 150 it is all of them.

9

In the interview

Extra depth · not in the video
What to say when you split data across machines

“The data doesn’t fit on one node, so I’ll shard it by key. I won’t use hash mod N, because adding a node would remap almost every key and we’d have to move nearly all the data. Instead, consistent hashing: nodes and keys hash onto the same ring and a key belongs to the next node clockwise, so adding a node moves only about 1/N of the keys, all from one neighbour. I’d give each node 100–200 virtual points so the load is even, store each key on the next three distinct nodes for replication, and keep the ring in the client library with the member list in etcd. The ring only decides ownership; the actual copying happens by snapshotting the one affected node.”

A worked design question

“Design a distributed cache (like Memcached) that holds 10 TB across many machines. How does a client find the right machine, and what happens when you add one?”

1 · Numbers

How many nodes

  • 10 TB at 64 GB of RAM per node → ~160 nodes, say 200 with headroom.
  • At 1 M requests/s, each node sees ~5,000/s. Fine for a cache.
  • Adding one node should move ~0.5% of keys (1/200), not 99.5%.
2 · Routing

Ring in the client

  • No proxy: the client library holds the sorted array (200 nodes × 150 points = 30,000 entries, tiny).
  • Lookup = one hash + one binary search, microseconds.
  • Member list in etcd; clients watch it and rebuild the array on change.
3 · Adding a node

For a cache, do nothing

  • A cache can afford misses: keys that moved are simply re-fetched from the database on first access.
  • So: add the node to etcd, clients re-route 0.5% of keys, 0.5% of requests miss once. No copying at all.
  • For a database you would do the snapshot-and-copy from section 5 instead.
4 · Trade-offs to name

Say them before being asked

  • Hot keys still hit one node → split or front with a local cache.
  • Clients with a stale member list talk to the wrong node → version the ring, nodes answer “moved”.
  • Redis Cluster’s hash slots do the same job with a simpler slot table; both are acceptable answers.

Likely follow-ups. Answer each out loud before opening it.

What problem does consistent hashing solve, in one sentence?

It decides which node owns a key in a way that changes the owner of as few keys as possible when nodes are added or removed: about 1/N of them instead of nearly all.

Why is hash mod N fine for API servers but not for a database?

API servers are stateless: any server can handle any request, so it does not matter that the mapping changed. A database node holds the data for its keys, so a changed mapping sends requests to nodes that do not have the data, and you must move it first.

How much data moves when you add a node?

With the ring, about 1/(N+1) of the keys, which is the minimum possible, and all of them come from one neighbour (or, with virtual nodes, a little from each node). With modulo, about N/(N+1): going from 3 to 4 nodes moves 75% of keys, from 10 to 11 moves 91%.

Is consistent hashing a service?

No. It is a function plus a sorted array of node positions, living in the proxy or in a client library inside each API server. The only shared thing is the member list, which comes from gossip or a coordination service like etcd.

What goes wrong with one point per node, and how do virtual nodes fix it?

Three random points make three random-sized gaps, so one node can own half the ring. Adding a node relieves only its one neighbour, and removing a node dumps all its keys on one neighbour.

Virtual nodes give each machine 100–200 points. The gaps average out, load is even within a few percent, a dead node’s keys spread over everyone, and a bigger machine can take more points.

How do you replicate on the ring?

Store each key on the first R distinct physical nodes clockwise from it, typically R = 3. Dynamo calls that the preference list. With virtual nodes you skip points that belong to a machine already in the list.

Does consistent hashing solve hot keys?

No. It balances the number of keys, not the traffic per key. A viral key still lands on one node. Handle it with a cache in front, by splitting the key into several copies, or with a bounded-load variant that spills overflow to the next node.

How do clients find out the ring changed?

Either the nodes gossip membership and clients ask any node, or the member list lives in a coordination service that clients watch. Version the ring so a node that receives a key it no longer owns can reply “moved” instead of serving stale data.

What would you use instead, and when?

Redis Cluster’s fixed hash slots with a slot-to-node table, when you want the same benefit with a simpler model. Rendezvous hashing when there are only a few nodes and you want no data structure. Range partitioning when you need range scans, since hashing destroys order.

Write the lookup on the whiteboard.

Keep a sorted array of (position, node). To look up a key: compute hash(key), binary-search for the first position greater than or equal to it, and if you run off the end, wrap to index 0. Adding a node is an insert into the sorted array; removing is a delete. That is the whole algorithm.

What does consistent hashing not do?

It does not move data, does not replicate, does not detect failures and does not balance traffic. It only answers “who owns this key” in a stable way. Everything else is a separate part of the design.
