Client-Server Model & Communication Protocols

How two machines talk: who asks, who answers, what carries the bytes, and what the bytes mean. These notes cover TCP, HTTP and WebSocket as the lesson explains them, then go deeper on the parts an interviewer will push on.

21 min 15 s video Blue sections · from the video Amber sections · extra depth

The whole lesson in six lines

  1. One machine (the client) asks for something. Another (the server) does the work and answers. They talk over the network.
  2. Almost all of that talk rides on TCP, which delivers bytes reliably. Opening a TCP connection costs three messages; closing it costs two.
  3. A TCP connection does not close by itself after data is sent. It stays open until the client or the server closes it, or the network breaks.
  4. TCP does not care what the bytes mean. The format both sides agree on is the protocol. HTTP is the common one, but you can invent your own.
  5. HTTP/1.1, as usually used: one request, one response, close. You pay the open-and-close cost again and again, unless the Connection: keep-alive header keeps the connection open.
  6. WebSocket: open once, stay open, and either side sends whenever it wants. Use it only when the server must push data in real time — chat, live likes, stock prices.

1

The client-server model

From the video▶ 0:00

This is the most common way two machines talk to each other. One machine plays the client: it asks for something to be done. The other plays the server: it does the heavy work and sends back the result.

Every request has the same shape — “hey server, do this for me”:

  • Give me the profile with this ID.
  • Delete the post with this ID.
  • Start a new virtual machine for me.
  • Send an email to this user.

“Client” does not only mean a person’s device. It can be a web browser, a phone app, or another backend server. Whoever is asking is the client for that conversation.

What do two separate machines have in common? Only the network between them. So all communication between client and server travels over the network, and the rest of this lesson is about the rules for that travel.

2

TCP: the reliable pipe underneath

From the video▶ 0:59

There are two well-known sets of rules for moving data between machines: TCP and UDP. The lesson’s position is simple. UDP matters for a small set of special applications. Almost everything else — web apps, backend APIs, databases — uses TCP. So the lesson sets UDP aside and goes deeper on TCP.

Why TCP? Because it is reliable. You hand it some data, and it takes care of cutting the data into small pieces, sending them, putting them back in the right order on the other side, and re-sending any piece that got lost on the way. Your code never has to think about that.

You do not need TCP’s internals for system design, but you must know three things about how its connections behave.

Property 1 · ▶ 2:01

Opening takes three messages

Before any real data moves, the client says “can we talk?”, the server says “yes”, and the client confirms. This is the three-way handshake.

Each message crosses the whole network. If the two machines are far apart, that is slow. So opening a connection is expensive.

Property 2 · ▶ 3:09

Closing takes two messages

When either side is finished, it says “please end this connection” and the other side says “OK”. The lesson calls this the two-way teardown.

So a connection that is opened and closed always costs 3 + 2 extra messages.

Property 3 · ▶ 3:45

It does not close by itself

Many people think the connection ends once the response arrives. It does not. TCP has no such rule.

It ends only when the network between the two breaks, or when the client or the server chooses to close it. Until then it stays open — almost forever.

Key idea

TCP never forces a connection to end. The client and the server decide when to close it. Keep this in mind — both keep-alive (section 4) and WebSocket (section 5) are built on it.

3

A protocol is just an agreed format

From the video▶ 5:05

TCP moves bytes from one machine to another. That is all. It does not say what those bytes should be, and it does not understand them.

So the client and the server must agree on a format. The lesson compares it to people: if I speak a language you do not know, my words reach your ears but you cannot act on them. We need a common language. Between machines, that common language is called a protocol.

The layer below

TCP — delivery

Gets the bytes across reliably and in order. Has no idea whether they are a web page, a chat message or a database command.

The layer on top

The protocol — meaning

Says how to read those bytes: where a message starts and ends, which part is the command, which part is the data. HTTP, WebSocket and Redis’s own format all live here.

HTTP is the common language ▶ 6:55

By far the most common protocol is HTTP. The client writes its request in the HTTP format. The server sees bytes in that shape, recognises them as an HTTP request, does the work, and writes the answer in the HTTP response format, which the client understands in turn.

HTTP has a written specification — what a request line looks like, what headers are, where the body goes — so that any client and any server built by different people can still understand each other. That is why the web runs on it.

You can define your own ▶ 8:11

Because TCP does not insist on HTTP, nothing stops you from inventing a format. The lesson’s example is a small key-value store (a database that only saves and fetches values by name). Its whole protocol could be:

# client sends this text over the TCP connection, ending with a newline
GET username\n

# server reads up to the newline, splits on the space:
#   first word  = the command to run   (GET)
#   the rest    = its arguments        (username)

If your client sends data this way and your server knows how to read it, you have a working protocol.

This is not just theory. Redis, a very popular in-memory database, does not use HTTP to get, set or delete a key. It defines its own format, tuned for its own job. Many databases and tools do the same. The price is that you need a special client library that speaks that format, because a browser or a generic HTTP tool cannot.

Key idea

TCP delivers the bytes. What the bytes mean is up to you. Most APIs you write will speak HTTP, but HTTP is a choice, not a law. Stay open to other options.

4

HTTP/1.1 and the keep-alive header

From the video▶ 10:50

HTTP comes in several versions: HTTP/1.1, HTTP/2 and HTTP/3. HTTP/1.1 is still the most widely used in production. Part of the world has moved to HTTP/2 and a small part to HTTP/3, and both are improvements built on the same ideas. So HTTP/1.1 is the minimum you must know. The lesson gives four points.

  1. It needs a TCP connection first. Before the client can send an HTTP request, the three-way handshake has to happen.
  2. The connection is typically closed once the response is sent. Client sends a request, server sends the response, and the server ends the connection.
  3. So you get almost a new connection for every request. To carry one request and one response you pay three messages to open and two to close. That is expensive.
  4. Hence the Connection: keep-alive header. The client adds it to the request to say: “please do not close this, I may use it again.” If the server supports the header, it leaves the connection open and the next request skips the handshake. Whether to honour it is the server’s decision.

Notice how this ties back to section 2. TCP itself never asked for the connection to be closed. Closing after each response is a habit of how HTTP is used, and keep-alive is simply the client and server agreeing not to do it. As the lesson puts it: there are no hard rules here, everything is flexible.

Note added · not in the video

The cost argument above is exactly right. One detail is worth correcting before an interview: in the official HTTP/1.1 standard, connections stay open by default. Closing after every response was the behaviour of the older HTTP/1.0. Section 7.2 explains.

5

WebSocket: when the server needs to speak first

From the video▶ 14:05

With HTTP, the client always speaks first. The server can only answer. It can never start a message on its own. The lesson calls this one-directional communication.

That is a real limit. Think of a messaging app. A new message for you has arrived at the server — how does it reach your phone?

The HTTP way: keep asking ▶ 15:05

Your app asks the server every few seconds: “any new message? any new message? any new message?” This is called short polling. It works, but it is wasteful. Most answers are “no”, every ask costs a request, and a message can sit on the server until the next ask.

The WebSocket way: the server pushes ▶ 15:45

WebSocket is a protocol built for bi-directional communication — both sides can send, at any time. Its key feature: the server can send data to the client without the client asking for it.

How it works:

  1. The client opens the connection. It has to be the client, because the server does not know the client’s address until the client reaches out.
  2. This is a normal TCP connection, opened with the normal three-way handshake.
  3. After that, nobody closes it. It stays open until one side decides to end it or the network breaks.
  4. Messages flow in both directions, one after another, for as long as it is open.

Why it is fast ▶ 16:47

Because the connection is set up only once, there is no handshake and no teardown around each message. The only delay left is the time to send the data itself. That is what people mean by low latency — a short wait between something happening and you seeing it.

Compare that with doing the same over HTTP/1.1 as described in section 4: handshake, one request, one response, teardown — and then all of it again for the next message.

Then why not use WebSocket for everything? ▶ 17:51

Because open connections are costly. Every connection that stays open takes up resources on your server, even when nothing is being sent. Keeping thousands or millions of them alive, and managing them, is a real burden — the lesson calls it “a huge pain”.

So a permanent connection only makes sense when you truly need one. For ordinary request-and-response work, most companies simply accept the overhead of HTTP, because it is fine.

The lesson’s rule

Whenever you need “real-time”, “low-latency” communication with your end user over the internet, and the server has to push data without being asked, think WebSocket. Examples from the lesson: chat, live likes floating up on a live stream, and stock prices that tick every second in a trading app.

7

Going deeper

Extra depth · not in the video

The lesson stops at section 6. This section adds the precise details behind its simplified picture, and the follow-up topics an interviewer is likely to raise.

7.1 · The handshake, with its real names and real cost

The three setup messages have names. The client sends SYN (“synchronise”), the server replies SYN-ACK, and the client replies ACK (“acknowledged”).

Closing is slightly more than the lesson’s two messages. A TCP connection is really two one-way streams, and each side closes its own: it sends FIN (“finished”) and the other side replies ACK. So a full, polite close is up to four messages. The lesson’s “I am done / OK” is one half of that. The idea is the same: closing is extra traffic.

A more useful way to count the cost is in round trips — one message there and one back.

  • The TCP handshake costs one round trip before the client can send its request.
  • HTTPS adds encryption, which needs its own handshake (called TLS) on top: one more round trip with the current version, TLS 1.3, and two with the older TLS 1.2.

If a round trip between a user in India and a server in the US takes 200 ms, a brand-new HTTPS connection spends about 400 ms saying hello before the first request even leaves. That is why reusing connections matters so much.

7.2 · Keep-alive is actually the default in HTTP/1.1

The lesson says an HTTP/1.1 connection is typically closed after each response unless you send Connection: keep-alive. The cost reasoning is correct, but the versions are mixed up slightly.

VersionWhat happens after a responseHow to change it
HTTP/1.0 (older)The connection is closedSend Connection: keep-alive to ask for it to stay open
HTTP/1.1The connection stays open, by defaultSend Connection: close to ask for it to be closed

Three practical points follow.

  • “Open” does not mean forever. Servers close a connection that has been idle for a while (the timeout is a setting, often some seconds to a minute or so), to free up resources.
  • Backends do the same thing on purpose. A service keeps a small set of already-open connections to its database and to other services, and reuses them. This is called a connection pool. It is keep-alive, applied inside your own system.
  • One request at a time. On a single HTTP/1.1 connection, the next request has to wait until the previous response has fully arrived. To load a page faster, browsers open several connections to the same site in parallel (about six).

7.3 · What HTTP/2 and HTTP/3 change

  • HTTP/2 lets many requests and responses share one TCP connection at the same time, instead of waiting in line. So one connection is enough, and the handshake is paid once.
  • HTTP/3 does not use TCP at all. It runs on a newer protocol called QUIC, which is built on UDP. Setup is quicker, and one lost piece of data no longer holds up every other request on the connection. This is what the lesson means when it says HTTP “can also happen over UDP”.

The meaning of a request — methods, headers, status codes — is the same in all three. Only the way it is carried changes.

7.4 · UDP in plain words

The lesson skips UDP. One table is enough for an interview.

TCPUDP
Setup before sendingHandshake firstNone — just send
If a piece is lostIt is sent againIt is gone

SpeedSlower — waits to get things rightFaster — never waits
Good forAnything that must arrive complete: web pages, APIs, payments, filesAnything where late data is useless: voice and video calls, online games, DNS lookups

The reasoning to remember: on a video call, if a fraction of a second of sound is lost, re-sending it later would only make things worse. You would rather skip it and stay live. That is when UDP wins.

7.5 · Four ways to get updates from a server

The lesson compares short polling with WebSocket. There are two options in between, and interviewers often ask you to choose among all four.

MethodHow it worksUse it when
Short pollingClient asks every few seconds. Server answers at once, usually “nothing new”.Updates are rare and a delay of a few seconds is fine. Simplest to build.
Long pollingClient asks. Server holds the request open and answers only when it has something (or a timeout hits). Client then asks again.You need near-instant updates but cannot use the options below.
Server-Sent Events (SSE)Client makes one ordinary HTTP request. Server keeps the response open and writes events into it as they happen. One direction only: server to client.Only the server needs to push: notifications, live scores, a progress bar.
WebSocketOne connection, open both ways, either side sends at any time.Both sides send often: chat, multiplayer games, shared editing.

A quick test: does the client also need to send a lot, quickly? If yes, WebSocket. If only the server pushes, SSE is simpler because it is plain HTTP. If updates are rare, polling is fine.

7.6 · How a WebSocket connection really starts

A WebSocket begins life as a normal HTTP request. The client adds a header that says, in effect, “I would like to switch this connection to WebSocket”:

GET /chat HTTP/1.1
Host: example.com
Connection: Upgrade
Upgrade: websocket

If the server agrees, it answers with the status 101 Switching Protocols. From that moment the same TCP connection stops carrying HTTP and starts carrying WebSocket messages in both directions.

The reason for starting with HTTP is practical: it lets WebSocket pass through the same ports and the same network equipment that already allow web traffic. Addresses start with ws://, or wss:// for the encrypted version, just like http:// and https://.

7.7 · Why WebSockets are hard to run at scale

The lesson says managing WebSockets is a pain. Here is what the pain is made of.

  1. Every open connection uses memory, even when silent. One million users online means one million open connections that some server must hold.
  2. The servers are no longer interchangeable. With plain HTTP any server can answer any request. With WebSocket, a user is attached to the one server holding their connection. If user A is connected to server 1 and user B to server 2, server 1 cannot reach B directly. You need something in the middle that passes messages between servers — a message bus, often built with a publish/subscribe tool such as Redis pub/sub.
  3. The load balancer must allow long-lived connections and not cut them off as “idle”.
  4. Every deploy disconnects everyone on the restarted servers. All those clients reconnect at the same moment and can flood you. Clients should wait a short random time before retrying.
  5. Dead connections look alive. If a phone loses signal, the server may not notice. Both sides send small “are you there?” messages (called heartbeats, or ping/pong) to find out.

7.8 · What the formats actually look like on the wire

Section 3 said HTTP is “just a format”. Here it is. This text is literally what travels over the TCP connection:

# request
GET /profile/42 HTTP/1.1
Host: api.example.com
Connection: keep-alive

# response
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 26

{"id": 42, "name": "Asha"}

And here is the same kind of “get me a value” request in Redis’s own format. It is more compact and quicker for a program to read, but only a Redis client knows how to write it:

*2\r\n$3\r\nGET\r\n$4\r\nname\r\n

# *2  = two parts follow
# $3  = the next part is 3 bytes long  -> GET
# $4  = the next part is 4 bytes long  -> name

Same job, two formats, one TCP underneath. That is the whole point of section 3.

8

Hands-on lab

Exercise from the video▶ 19:26 · commands added here

The lesson sets two tasks. First, if you have never done it, write a simple HTTP API in any language — for example a to-do app that saves items to a database and reads them back. Second, and more important: build a chat application with Socket.IO, to feel the difference when the server pushes data without being asked.

The steps below warm up with two one-minute experiments, then build the chat. You need Node.js installed for steps 3 to 5.

  1. Watch one HTTP exchange

    The -v flag makes curl print everything. Lines starting with > are the request it sent. Lines starting with < are the response. Compare them with section 7.8.

    curl -v http://example.com/
  2. Watch a connection being reused

    Ask for the same address twice in one command. Before the second request, curl prints a line saying it is re-using the existing connection. No second handshake — that is keep-alive at work.

    curl -v http://example.com/ http://example.com/
  3. Set up the chat project

    Socket.IO is the library the lesson recommends. Express is a small web server library used here to serve the page.

    mkdir chat && cd chat
npm init -y
npm install express socket.io
  4. Write the server and the page

    The server does one thing: whenever any client sends a chat message, it pushes that message to every connected client. That push is the part plain HTTP cannot do.

    // server.js
const express = require('express');
const { createServer } = require('node:http');
const { join } = require('node:path');
const { Server } = require('socket.io');

const app = express();
const server = createServer(app);
const io = new Server(server);

app.get('/', (req, res) => {
  res.sendFile(join(__dirname, 'index.html'));
});

io.on('connection', (socket) => {
  socket.on('chat message', (msg) => {
    io.emit('chat message', msg);   // push to everyone
  });
});

server.listen(3000, () => {
  console.log('chat running at http://localhost:3000');
});
    <!-- index.html -->
<ul id="messages"></ul>
<form id="form">
  <input id="input" autocomplete="off"><button>Send</button>
</form>

<script src="/socket.io/socket.io.js"></script>
<script>
  const socket = io();   // opens the connection
  const form = document.getElementById('form');
  const input = document.getElementById('input');
  const messages = document.getElementById('messages');

  form.addEventListener('submit', (e) => {
    e.preventDefault();
    if (input.value) {
      socket.emit('chat message', input.value);
      input.value = '';
    }
  });

  socket.on('chat message', (msg) => {   // runs when the server pushes
    const item = document.createElement('li');
    item.textContent = msg;
    messages.appendChild(item);
  });
</script>
  5. Run it and watch the messages travel

    Start the server and open http://localhost:3000 in two browser tabs. Type in one tab; the message appears in the other at once, although that tab never asked for it.

    node server.js

    Then open the browser’s developer tools, go to the Network tab and filter by “WS”. Click the connection and open its Messages view. You will see the 101 Switching Protocols answer from section 7.6, and then each chat message passing over that one connection.

Try next

Stop the server with Ctrl+C and start it again while a tab is open. The page reconnects by itself — that is Socket.IO doing the reconnect work from section 7.7. Then try the lesson’s other idea: build the same chat with short polling over plain HTTP and compare how it feels.

Good to know

Socket.IO is not plain WebSocket. It is a library built on top of it that adds automatic reconnecting, chat rooms, and a fallback to HTTP long polling when a WebSocket cannot be opened. You may even see a few polling requests in the Network tab before the WebSocket appears. A plain WebSocket client cannot talk to a Socket.IO server — both ends must use Socket.IO.

9

In the interview

Extra depth · not in the video
What to say when you draw the line between client and server

“Clients talk to our API over HTTPS. Connections are kept alive and reused, so we are not paying a handshake on every request. For the live part of the product the server has to push, so those clients also hold a WebSocket to a separate gateway service. The gateways are stateful, so I’d put a publish/subscribe layer behind them to route each message to whichever gateway holds the receiver’s connection. Everything else stays plain request and response, because open connections cost memory and make deploys harder.”

Likely follow-ups. Answer each out loud before opening it.

Why is opening a new connection for every request slow, and what do you do about it?

Each new connection needs a TCP handshake, and with HTTPS an encryption handshake on top. That is one to three round trips across the network before any useful data moves, plus the close at the end.

The fix is to reuse connections: keep-alive between browser and server, connection pools between our services and the database, and HTTP/2 so many requests can share one connection at the same time.

If WebSocket is faster, why not use it for everything?

It is faster per message, but each user holds an open connection that costs memory even when idle. Servers become stateful, so scaling, load balancing and deploys all get harder.

Most API calls are a single ask and a single answer, where none of that pays off. So WebSocket is used only where the server must push or messages are very frequent.

Short polling, long polling, Server-Sent Events or WebSocket — how do you choose?

Ask two things: who needs to send, and how fresh must the data be?

Updates are rare and a few seconds’ delay is fine: short polling. Only the server pushes: Server-Sent Events, because it is plain HTTP and simple. Both sides send often and it must feel instant: WebSocket. Long polling is the fallback when the other two cannot be used.

User A is connected to server 1 and user B to server 2. How does A’s message reach B?

Server 1 cannot push to B, because B’s connection lives on server 2. So server 1 publishes the message to a shared message bus, such as Redis pub/sub. Server 2 is subscribed, receives it, and pushes it down B’s WebSocket.

The message is also saved to the database, so B still gets it later if they were offline at that moment.

What happens to WebSocket users when you deploy a new version?

Every connection on a restarted server is dropped. Clients must reconnect on their own, after a short random wait so they do not all arrive in the same second.

On our side we restart servers a few at a time, and stop sending new connections to a server before shutting it down. Anything missed while disconnected is fetched from the database after reconnecting.

When would you pick UDP over TCP?

When being on time matters more than being complete. In a voice or video call or a fast game, a lost piece of data is useless by the time it could be re-sent, so it is better to skip it and stay live.

For anything that must arrive whole and in order — API calls, payments, files — TCP.

Do our internal services have to talk HTTP to each other?

No. TCP carries any format the two sides agree on. Databases such as Redis use their own. Many companies use gRPC between services, which sends compact binary messages over HTTP/2.

The trade-off: a custom or binary format is faster and smaller, but harder to inspect and needs special client libraries. Plain HTTP with JSON is slower but every tool and every engineer understands it.
