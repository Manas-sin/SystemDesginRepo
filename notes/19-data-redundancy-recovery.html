Data Redundancy & Recovery

Servers are easy to replace. Data is not. These notes cover what the lesson says about keeping extra copies of your data, then go deeper on the parts an interviewer will push on.

8 min 34 s video Blue sections · from the video Amber sections · extra depth

The whole lesson in five lines

  1. API servers hold no data, so losing one is harmless. The database holds all the data, so losing it stops everything.
  2. The only protection against losing data is to keep more than one copy of it. That is all “redundancy” means.
  3. Backup and restore: copy the data on a schedule — the changes daily, everything weekly — and keep one copy in another region. Cheap, but you lose whatever was written after the last backup.
  4. Continuous redundancy: run a second database (a replica) that receives every write as it happens. If the main one dies, the replica takes over almost at once.
  5. Critical data gets a live replica. Less critical data gets periodic backups.

1

Why the database is the hard part

From the video▶ 0:00

A typical backend has two kinds of machines.

API servers run your code. They keep nothing important on themselves; every request reads and writes through the database. A machine like this is called stateless — “state” just means remembered data, and it has none. Put several of them behind a load balancer (a box that spreads requests across them) and any one can answer any request. If one crashes, only the requests it was handling at that instant fail. The rest carry on.

The database is the opposite. It is stateful: it is where the data actually lives. If it goes down, every API server is healthy but useless. In most cases that is a complete outage.

There are two levels of bad here, and the lesson cares about the worse one.

Bad

The database goes down

The machine restarts, or the database software crashes. You are offline until it comes back, but the data is still sitting on the disk.

Worst

The disk itself dies

The data is gone. Restarting fixes nothing, because there is nothing left to start from. This is the case you must plan for.

Key idea

A good design always has an answer to: “the disk holding our data just died — now what?” “We had no backup” is not an answer.

2

The one idea: keep more than one copy

From the video▶ 1:09

The only way to protect yourself against losing data is to have another copy of it somewhere else. That is what data redundancy means: storing the same data more than once, on purpose.

With a second copy you can always get back to the last known good point — the most recent moment for which you still hold a healthy copy. Everything else in this lesson is a different way of making that copy. The methods differ mainly in one thing: how old the copy is at the moment you need it.

You make two choices.

Choice 1

How much do you copy?

  • A row or document — copy single records as they change.
  • A table — dump one table and recreate it elsewhere.
  • The whole database — dump everything.
Choice 2

Where does the copy live?

  • A different table in the same database.
  • A different database on another machine.
  • A different region — another part of the world.

The further away the copy lives, the bigger the failure it survives. A copy on the same disk does not survive that disk dying. A copy in the same building does not survive a flood in that building.

3

Method one: backup and restore

From the video▶ 2:17

The simplest method. Every so often, save a copy of the data to a file and store it somewhere safe. When something goes wrong, load the most recent file into a fresh database. The lesson gives three habits.

Daily

Back up the changes

Take one complete backup, then each day save only what changed that day. This is an incremental backup. It is small and quick, so you can afford it daily. Crash today and you still have everything up to yesterday.

Weekly

Back up everything

Once a week — say every Sunday — take a full backup no matter what. If a daily file turns out to be broken, you still have a clean starting point that depends on nothing else.

Elsewhere

One copy in another region

Send a copy to a data centre far away. If a flood or fire takes out the whole data centre, your data still exists. This part is called disaster recovery.

What you get
  • Almost always the easiest thing to set up.
  • Cheap — backup files only need storage.
  • When something goes wrong, the fix is simple: restore the last backup.
What you give up
  • The copy is always a bit old. Anything written after the last backup is lost.
  • Restoring takes time. A big database can take hours to load, and you are offline while it does.
Why bother if it loses a day?

Some data is far better than no data. With yesterday’s data the business keeps running; with none it does not. API servers can be recreated in minutes. Data cannot be recreated at all.

4

Method two: continuous redundancy

From the video▶ 4:24

A backup is a copy made now and then. Continuous redundancy means keeping a second copy up to date all the time.

You run a second database, the replica, next to the first one, the main (also called master or primary). Every write that reaches the main also reaches the replica, so at any moment you hold two live copies.

If the main’s disk dies, you make the replica the new main and point the API servers at it. This switch is called failover. It happens almost instantly, compared with the hours a restore can take.

How does a write reach the replica? Two ways. ▶ 5:43

Either way the goal is the same: a real-time duplicate, so nothing is missed.

The replica here is a standby ▶ 6:26

In this lesson the replica has one job: to exist. It serves no user traffic — no reads, no writes. It only stays in sync so that it can step in when the main is gone.

(Replicas can also be used to share read traffic. That is a different goal — handling more load, not safety.)

Be precise about what this protects

A replica saves you when a disk or a machine dies. On its own it is not disaster recovery: if both databases sit in the same data centre and that data centre is lost, both copies are lost. You still need the copy in another region from section 3.

5

Picking between them

From the video▶ 6:10

The lesson’s rule is short: some data matters more than other data. More critical data gets continuous redundancy. Less critical data gets periodic backups.

Side by side:

Backup and restoreStandby replica
How old is the copy?Up to a day, or whatever your schedule isSeconds at most
Data lost in a crashEverything since the last backupLittle or nothing
Time to get back onlineMinutes to hours — the files must be loadedSeconds to minutes — just switch over
CostLow — only storage for filesHigh — a second full database running all the time
Good forLogs, analytics, anything you could live without for a dayOrders, payments, user accounts
6

Going deeper

Extra depth · not in the video

The lesson stops at section 5. These are the follow-up questions an interviewer is likely to ask next.

6.1 · Two numbers drive every decision

Before choosing a method, ask the business two questions.

  • How much data can we afford to lose? Measured in time: “at most 5 minutes of writes.” The industry name is RPO (recovery point objective).
  • How long can we afford to be down? “At most 10 minutes.” The name is RTO (recovery time objective).

6.2 · A replica is not a backup

This is the most common trap. A replica faithfully copies everything — including mistakes. If someone runs a DELETE that wipes the orders table, or a bug writes garbage, the replica has the same damage a moment later. Now you have two copies of broken data.

Only a backup can take you back in time, to before the mistake. So the two methods are not rivals. They cover different failures.

What went wrongDoes a replica help?Does a backup help?
A disk or machine diesYes — switch overYes, but slower and with some loss
Data deleted by mistake, or corrupted by a bugNo — the mistake is copied tooYes — restore to before it happened
The whole data centre is lostOnly if the replica is in another regionOnly if a copy is kept in another region
Takeaway

Real systems run both: a replica for fast recovery from hardware failure, and backups to undo mistakes.

6.3 · Synchronous or asynchronous: the real trade-off

The whole question is: when does the main tell the user “saved”?

Synchronous

Wait for the replica, then answer

  • + If the main dies, nothing is lost. Every confirmed write is on two machines.
  • − Every write is slower, because it waits for a network round trip.
  • − If the replica is slow or unreachable, writes stall.
Asynchronous

Answer now, copy afterwards

  • + Writes stay fast. A replica problem never blocks users.
  • − The replica is always slightly behind. This gap is called replication lag.
  • − If the main dies, the last few writes that were not yet forwarded are gone.

Rule of thumb. Money, and anything you told the user was saved: synchronous, to at least one nearby replica. Everything else: asynchronous. Across regions it is almost always asynchronous, because the distance would make every write slow.

Many databases also offer a middle setting: wait until one replica has received the write, but not until it has finished applying it. MySQL calls this semi-synchronous replication.

6.4 · Why “the API writes to both” is risky

Way 1 from the lesson looks simple, but two separate writes cannot easily be made all-or-nothing.

  • The write to the main succeeds and the write to the replica fails because of a network blip. The copies now disagree, and nothing notices.
  • Two requests change the same row at nearly the same time. The main sees A then B; the replica sees B then A. They end up with different values.

So in practice you let the database do the copying (Way 2). The main keeps an ordered log of every change, and the replica replays that same log in the same order, so the two cannot drift apart like this. That built-in feature is what people normally mean by “replication.” It can run in synchronous or asynchronous mode.

6.5 · Failover is harder than it sounds

Three things have to go right.

  1. Detect that the main is truly dead, and not just slow for a few seconds.
  2. Promote the replica and point every API server at it.
  3. Fence off the old main. If it comes back still believing it is the main, two databases accept writes and their data splits apart. This is called split brain.

In an interview you do not need to build this. Say you would use the managed database’s automatic failover, and name these three risks.

6.6 · Going back to an exact moment

Daily backups only take you back to last night. To do better, databases also keep a running log of every change (MySQL calls it the binary log; PostgreSQL the write-ahead log). Restore last night’s backup, then replay the log up to one second before the mistake. This is point-in-time recovery. It is the answer to “someone dropped the table at 2:07 pm.”

6.7 · Two habits that make backups real

  • Test the restore. A backup you have never restored is a hope, not a backup. Restore to a scratch server on a schedule and check the data.
  • The 3-2-1 rule. Keep 3 copies of the data, on 2 different kinds of storage, with 1 in a different location.

6.8 · What this looks like on a cloud database

You rarely build any of this by hand. Each idea in the lesson maps to a switch on a managed database. On AWS RDS, for example:

Idea from the lessonOn AWS RDS
Daily and weekly backupsAutomated backups — a daily snapshot plus the change log, with point-in-time recovery (usually to within the last 5 minutes)
Standby replica that serves no trafficMulti-AZ — a synchronous standby in another zone, with automatic failover in about 1–2 minutes
One copy in another regionCross-region backup copies, or a cross-region read replica (asynchronous)

A “zone” (availability zone) is a separate data centre inside the same region.

7

Hands-on lab

Exercise from the video▶ 7:03 · commands added here

The lesson ends with three tasks: set up replication between two MySQL servers, back up a MySQL database, and restore it. Here is one way to do all three on a laptop with Docker and MySQL 8.4. Allow about 20 minutes.

  1. Start two MySQL servers

    Each server needs its own server-id. The two gtid flags give every change a unique ID, so the replica can work out by itself which changes it is missing. Wait about 30 seconds for both to start.

    docker network create dbnet

docker run -d --name db-main --network dbnet -e MYSQL_ROOT_PASSWORD=root \
  mysql:8.4 --server-id=1 --gtid-mode=ON --enforce-gtid-consistency=ON

docker run -d --name db-replica --network dbnet -e MYSQL_ROOT_PASSWORD=root \
  mysql:8.4 --server-id=2 --gtid-mode=ON --enforce-gtid-consistency=ON
  2. On the main: create a login for the replica

    The replica connects to the main like any other client, so it needs a user that is allowed to read the change log.

    docker exec -it db-main mysql -uroot -proot
    CREATE USER 'repl'@'%' IDENTIFIED BY 'repl_pass';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
  3. On the replica: tell it who to follow

    In the status output, look for Replica_IO_Running: Yes and Replica_SQL_Running: Yes. Seconds_Behind_Source is the replication lag.

    docker exec -it db-replica mysql -uroot -proot
    CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = 'db-main',
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = 'repl_pass',
  SOURCE_AUTO_POSITION = 1,
  GET_SOURCE_PUBLIC_KEY = 1;
START REPLICA;
SHOW REPLICA STATUS\G
  4. Watch a write travel

    Write on the main, read on the replica. This is asynchronous replication — Way 2 from section 4.

    -- on db-main
CREATE DATABASE shop;
CREATE TABLE shop.orders (id INT PRIMARY KEY AUTO_INCREMENT, item VARCHAR(50));
INSERT INTO shop.orders (item) VALUES ('keyboard'), ('mouse');

-- on db-replica: both rows are here
SELECT * FROM shop.orders;
  5. Take a backup

    Run this in your normal terminal, not inside MySQL. --single-transaction takes a consistent picture without locking the tables. Open shop_backup.sql afterwards: it is plain SQL that rebuilds the database.

    docker exec db-main mysqldump -uroot -proot --single-transaction \
  --set-gtid-purged=OFF --databases shop > shop_backup.sql
  6. Break it, then restore

    Drop the table on the main and check the replica. It is gone there too — a replica is not a backup (section 6.2). Then load the backup file. The table comes back on the main, and replication carries the restore to the replica as well.

    -- on db-main: the "mistake"
DROP TABLE shop.orders;

-- on db-replica: the table is gone here too
SELECT * FROM shop.orders;
    docker exec -i db-main mysql -uroot -proot < shop_backup.sql
  7. Clean up 
    docker rm -f db-main db-replica
docker network rm dbnet
Try next

Stop the replica (docker stop db-replica), write a few rows on the main, start it again and watch it catch up. Then stop the main and promote the replica by running STOP REPLICA; RESET REPLICA ALL; on it — that is a failover done by hand.

8

In the interview

Extra depth · not in the video
What to say when you draw the database box

“The database is the one stateful piece, so I’d protect it three ways. A standby replica in a second zone with automatic failover, so a dead machine costs us about a minute. Daily incremental and weekly full backups with point-in-time recovery, so we can undo a bad delete. And a copy of the backups in another region, in case we lose the whole region. For payments I’d make replication synchronous so a confirmed payment is never lost. For everything else, asynchronous is fine.”

Likely follow-ups. Answer each out loud before opening it.

The main database’s disk just died. Walk me through what happens.

The replica is promoted to main and the API servers are pointed at it. Users see a minute or two of errors.

With synchronous replication no confirmed write is lost. With asynchronous we may lose the last second or so.

Then we build a fresh replica from the new main, so we are back to two copies.

You already have a replica. Why still pay for backups?

A replica copies mistakes as faithfully as it copies good writes. A bad delete or a buggy release damages both copies within a second.

Backups are the only way to go back in time. The replica covers hardware failure; backups cover human and software failure.

A developer ran DELETE without a WHERE at 2:07 pm. Now what?

Restore last night’s backup onto a new server and replay the change log up to 2:06 pm. Then copy the missing rows back into production.

We do not roll the whole live database back, because that would also throw away every good write made after 2:07.

Synchronous or asynchronous replication — which would you pick?

It depends on what losing a write costs. For payments or orders, synchronous to one nearby replica: slower writes are worth never losing a confirmed one.

For likes, view counts or activity feeds, asynchronous: losing the last second in a rare crash is acceptable, and writes stay fast.

How do you survive losing a whole region?

The copy has to be in another region before the disaster. Ship backups there, and for faster recovery run an asynchronous replica there too.

Be honest about the cost: because it is asynchronous, a region failure can lose a few seconds of writes, and switching regions is a much bigger operation than a normal failover.

How often should we back up?

Work backwards from how much data the business can afford to lose. If a day is fine, daily backups are enough.

If it is minutes, add continuous saving of the change log so you can recover to any moment. If it is zero, you need synchronous replication.
