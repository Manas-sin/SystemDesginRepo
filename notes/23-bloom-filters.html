Bloom Filters

A Bloom filter is a few kilobytes of bits that can tell you, with certainty, that something is not in a set. These notes follow the lesson’s Instagram example, then go deeper on sizing, placement, and the follow-up questions interviewers ask.

20 min 28 s video Blue sections · from the video Amber sections · extra depth

The whole lesson in six lines

  1. A Bloom filter answers one question, “is X in the set?”, with one of two answers: definitely no or probably yes. It can never miss something that is really there.
  2. It is an array of bits. To add an item you hash it and switch a few bits on. The item itself is never stored, which is why the filter is tiny.
  3. The lesson’s problem: Instagram must not recommend a Reel you already watched. A set of watched IDs per user is exact, but it grows without end and has to be loaded into memory to be checked.
  4. The key insight: a watch cannot be undone. If you give up “remove”, you can also give up storing the IDs. Relax one constraint, gain a lot of space and speed.
  5. The price: as the bits fill up, the filter says “probably yes” for things that are not there (false positives). Its size is fixed when it is created, it cannot be grown or emptied, so size it for the maximum and rebuild it from the real database when needed.
  6. Use it wherever you insert but never remove, need a fast and certain “no”, and can live with an occasional wrong “yes”: feeds, recommendations, crawlers, and inside databases and caches.

1

The problem: don’t show it twice

From the video▶ 0:00

The lesson opens with the one-line definition: a Bloom filter is an approximate data structure (also called probabilistic) that says with 100% certainty that an element does not belong to a set. Everything else follows from that sentence.

The example is Instagram Reels. A recommendation engine must show you something new, never a Reel you already watched. So before it recommends a Reel it has to ask: “has this user seen this one?”

The first idea: a set per user ▶ 1:00

Keep a set of every post ID each user has ever watched. Before recommending, check the set. Present → skip it. Absent → recommend it. This works, and it is exact.

Then look at the scale. People watch hundreds or thousands of Reels a day. Over months, every user’s set becomes huge. And a set is not something you can check from disk: it is built as a tree or a hash table, so to check one key you load the whole set into memory. Millions of users × thousands of Reels × months means you cannot hold that in memory. It is expensive and slow.

The lesson’s question at this point: can we do better? That question is what gave rise to the Bloom filter.

2

The insight: you cannot un-watch

From the video▶ 2:50

A set gives you two operations: add and remove. But think about what a “view” is. Once you have watched a Reel, you do not un-watch it. The view is registered, and it stays registered. So for this problem we never need “remove”.

That is a constraint we can relax. And the lesson makes a general point here: almost every variant of a data structure starts this way. Drop something you do not need, and in exchange get something you do need, here much better space and time efficiency. You get some, you lose some. Computer science is trade-offs all the way down.

The crux

If we are never going to take an item out, do we even need to store the item? No. We only need to remember that it was added. That is what a Bloom filter stores: not the IDs, only the fact that they were seen.

3

How it works: bits and a hash

From the video▶ 4:16

Whenever you hear the word “filter” in this context it means a bit array: an array of single bits, not even bytes. A Bloom filter is a bit array invented by a researcher named Bloom (Burton Bloom, in 1970), hence the name.

The lesson’s example uses a filter of 8 bits, one byte, and stores words in it.

  1. Take the word apple. Pass it through a hash function (MD5, SHA, MurmurHash, any you like). Take the result mod 8, because there are 8 bits. Say you get 2. Set bit 2 to 1.
  2. Take ball. Same hash, mod 8. Say you get 6. Set bit 6 to 1.
  3. Take cat. Same hash, mod 8. Say you get 2 again. Bit 2 is already 1 from apple. Leave it at 1. That is fine.

The “mod 8” is simply “mod the length of the bit array”. A 10 KB filter would be mod (10 × 1024 × 8).

4

The two answers: “no” and “maybe”

From the video▶ 7:05

Now check for words. Same hash function, same mod 8, then look at that one bit.

  • dog → say 5. Bit 5 is 0. Nothing that was ever added could have landed on 5 and left it 0. So dog is definitely not in the set. Correct.
  • elephant → say 6. Bit 6 is 1. But we never added elephant; ball set that bit. The filter says “yes”, and it is wrong. This is a false positive.
The filter saysWhat it meansWhat you do
NoThe item was never added. 100% certain.Trust it. For Reels: safe to recommend.
YesThe item may have been added. Sometimes wrong.If being wrong matters, check the real store. For Reels: just skip it, no check needed.

Notice the second row for the recommendation case. Instagram does not go and verify a “yes”. It simply does not recommend that Reel. The cost of a false positive is one missed recommendation out of thousands, which nobody notices. What matters is that everything it does show is guaranteed new. That is exactly the situation where Bloom filters shine: the “no” is what you are buying.

Remember it this way

No false negatives, ever. Some false positives, by design. Space and time efficiency in exchange for a little correctness on one side only.

5

Filling up, sizing, and why it cannot grow

From the video▶ 10:07

The false positive rate rises as you add

Every item you add switches on bits. Keep adding and more and more bits are 1. Eventually all of them are 1, and then the filter says “yes” to every word you give it. Useless. So the false positive rate is not a fixed property of a filter; it starts near zero and climbs with the number of items inserted.

Here is that curve measured on a real filter (the one from the lab in section 8), sized for 1,000 items:

Items addedBits set to 1Wrong “yes” answers

1,000 (designed for)52%1.0%

4,00095%68%
8,000100%98%

At the designed load it behaves. At double the load it is already bad. At four times it is almost always wrong.

Size is fixed at creation ▶ 10:50

A Bloom filter is not something that grows on its own. When you create it you say how big it is. The lesson’s example is 1 KB: 1,024 bytes, so 8,192 bits. That is the whole filter, for ever.

So you must tune the size to the number of keys you will put in and the false positive rate you can accept. There is a standard formula for this; the lesson leaves it for you to look up, and section 7.1 gives it along with a rule of thumb.

Why you cannot grow or empty it ▶ 12:12

Say you started at 1 KB, inserted a million keys, and the false positive rate is now terrible. Two things you might want to do, and why neither works:

  • Take some items out. Impossible. Bits are shared between items (apple and cat both set bit 2). Clearing a bit for one item would wrongly remove others, which would break the one guarantee the filter has.
  • Make it bigger. Also impossible. Every position was computed as hash mod 8. Change the size to 16 and the same word now maps to a different bit. All existing bits are meaningless under the new mapping. This is the limitation of anything hash-based.

What you actually do is recreate it: make a new, larger filter, then go through all the keys again and insert them into the new one. Where do the keys come from? Not from the old filter; it does not have them. They come from the real database. The Bloom filter is never the source of truth. The list of Reels a user watched lives in a database somewhere. The filter is an auxiliary structure that makes checks fast. Rebuilding it means iterating the source of truth and re-inserting.

That is slow and fiddly, so in practice you over-provision: you know roughly how many keys you will store and what false positive rate you can tolerate, so you size the filter with room to spare from day one.

The three cannots

Cannot remove an item. Cannot grow. Cannot list what is inside. If your design needs any of these, see the variants in section 7.5, or do not use a Bloom filter.

6

Redis, and where to use it

From the video▶ 14:30

You do not have to build it

Redis offers Bloom filters as a native data structure (through its RedisBloom module). You create a filter, giving it the expected number of items and the error rate you want, add keys, and check keys. Use it as a black box. The lesson corrects itself on one point: Redis will not magically manage growth for you, so you still have to size it, and if it outgrows that size, re-ingesting the keys is your job. (Section 7.4 has the finer print on what Redis does when a filter fills.)

When a Bloom filter is the right tool ▶ 15:49

Use it when

All four are true

  • You insert but never remove.
  • You need very fast checks.
  • You need a “no” you can trust 100%.
  • An occasional wrong “yes” is acceptable.
Do not use it when

A wrong “yes” would hurt

If the filter saying “exists” about something that does not exist is not OK for you, a Bloom filter is not for you. That is the whole limitation, and it is a hard one.

7

Going deeper

Extra depth · not in the video

The lesson uses one hash function and leaves sizing “a Google search away”. These are the next things an interviewer will ask about.

7.1 · Why real filters use several hash functions

With one hash function, an item switches on one bit, and a stranger gets a false “yes” whenever its single bit happens to be set. If a third of the bits are set, a third of all strangers get a wrong “yes”. That is a lot.

Real filters use k hash functions. An item sets k bits; a stranger must hit k set bits at the same time to get a wrong “yes”. With k = 7, even when half the bits are set, the chance is ½ × ½ × … seven times ≈ 1%. More hash functions means fewer false positives, up to a point: each extra hash also fills the array faster. The best k for a given size and item count is:

bits needed    m = −n · ln(p) / (ln 2)²
hash functions k = (m / n) · ln 2
n = items you will insert · p = false positive rate you accept

You do not need to remember the formula. Remember the table it produces:

Bits per itemHash functions (k)False positive rate1 million items cost
~5310%0.6 MB
~1071%1.2 MB

The rule of thumb to say out loud

About 10 bits per item gives about 1% false positives. Every extra ~5 bits per item cuts the rate by 10×. So 100 million items at 1% is 1 billion bits = 120 MB, which fits in memory on one machine. A hash set of the same 100 million 8-byte IDs would need several gigabytes.

Two practical details. First, use a fast, non-cryptographic hash such as MurmurHash3 or xxHash; MD5 and SHA work but cost more CPU for no benefit here. Second, you do not run k different hash functions. You compute two hashes h1 and h2 and derive the rest as h1 + i·h2 for i = 0 … k−1 (the “double hashing” trick). The lab does exactly this.

7.2 · Where the filter lives

The lesson puts it in Redis. There are two sensible places, and interviewers like to hear you weigh them.

For the Reels problem you also choose between one filter per user (key seen:{user_id}, small, rebuilt from that user’s history alone) and one giant filter with user_id:post_id as the item. Per user is the usual choice: a filter that is too full only hurts one user, and inactive users’ filters can be dropped and rebuilt on demand.

7.3 · What “full” looks like in production, and the rotation trick

A filter past its design capacity does not crash and does not lie in the dangerous direction. It just says “maybe” more and more often. What that costs depends on the job:

  • In front of a database or disk: a saturated filter sends every lookup through. The system becomes exactly as slow as if the filter were not there. Slow, not wrong.
  • In a recommender or feed: every candidate looks “already seen”, so nothing is recommended. The feed quietly goes empty. This is the silent failure to watch for: monitor the fill level (Redis reports it in BF.INFO) and alert well before capacity.

When a filter does need replacing, do it without downtime:

  1. Build the new filter on the side

    Create seen:42:new with a larger capacity. Read the user’s full history from the database (the source of truth) and insert every ID.

  2. Keep both up to date while you build

    New views during the rebuild are added to both the old and the new filter, so the new one is not missing anything when it goes live.

  3. Swap atomically

    In Redis, RENAME seen:42:new seen:42 replaces the old key in one step. Readers never see a half-built filter and never see a missing one.

One finer point on Redis. The lesson says Redis cannot grow a filter. Strictly, RedisBloom creates a scalable filter by default: when the first filter reaches its capacity it adds a second, larger sub-filter behind it, and a check now consults both. So the key keeps accepting adds, at the price of slower checks and more memory per item. The lesson’s point still holds: nothing is ever removed, the first filter stays as full as it was, and if you got the initial capacity badly wrong you still want the rotation above.

7.4 · Where you have already met it

SystemWhat the filter does there
Cassandra, HBase, RocksDB, LevelDBThese databases write data into many files on disk. Each file has its own Bloom filter of the keys it holds. A read for a key checks the filters first and opens only the files that say “maybe”, instead of every file. This is the single biggest use of Bloom filters in the world, and the classic “deep dive” answer when an interviewer asks how a key-value store reads fast.
CDNs and caches (Akamai)Most objects are requested exactly once. Caching them wastes space. A filter remembers what has been requested before, and an object is cached only on its second request. Akamai reported this removed about three quarters of one-time objects from its caches.
Web crawlers“Have I fetched this URL?” across billions of URLs, as in the lesson.
Medium, Instagram-style feeds, TinderPer-user “already shown” filters, as in the lesson.
Browsers (Safe Browsing, historically)A local filter of known-bad URLs. “No” means the site is safe and the browser carries on; “maybe” triggers a real check with the server. The common case never leaves the machine.

7.6 · Limits worth saying out loud

  • It is a cache of a fact, not the fact. If the filter is lost, nothing is lost; rebuild it from the database. Design the rebuild path before you need it.
  • Size and hash functions are a contract. Two filters can only be merged (bit-wise OR gives the union) if they have the same size and the same hashes. Decide them once.
  • It balances no load and orders nothing. It cannot count how many times an item was added (that is a count-min sketch) or tell you which items are inside.
  • Hostile input. Someone who knows your hash function can craft keys that collide and inflate false positives. Where that matters, seed the hash with a secret.

Hands-on lab

Exercise from the video▶ 18:25 · code added here

The lesson’s exercise is to insert random keys into a Bloom filter and catch a false positive. Two versions below: one you build yourself in 30 lines (so the formula and the k hashes are not magic), and the Redis one the lesson asks for.

  1. Save this as bloom.py

    A filter sized by the formula from section 7.1. It inserts keys past its design capacity and measures the false positive rate against 20,000 keys that were never added.

    import hashlib, math, random

class BloomFilter:
    def __init__(self, n, p):
        # size the bit array for n items at false-positive rate p (the standard formula)
        self.m = math.ceil(-n * math.log(p) / (math.log(2) ** 2))   # number of bits
        self.k = max(1, round(self.m / n * math.log(2)))             # number of hash functions
        self.bits = bytearray((self.m + 7) // 8)                     # m bits, all 0
        self.count = 0

    def _positions(self, item):
        # one 128-bit hash, split into two halves; k positions = h1 + i*h2 (double hashing)
        d = hashlib.blake2b(item.encode(), digest_size=16).digest()
        h1, h2 = int.from_bytes(d[:8], "big"), int.from_bytes(d[8:], "big") | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, item):
        for pos in self._positions(item):
            self.bits[pos // 8] |= 1 << (pos % 8)
        self.count += 1

    def might_contain(self, item):
        return all(self.bits[pos // 8] >> (pos % 8) & 1 for pos in self._positions(item))

random.seed(1)
bf = BloomFilter(n=1000, p=0.01)
print(f"sized for 1,000 items at 1% -> m = {bf.m} bits ({bf.m // 8} bytes), k = {bf.k} hashes")

never_added = [f"ghost-{i}" for i in range(20000)]      # we will never add these
print(f"{'items added':>12} {'bits set':>9} {'false positives':>16}")
for target in (250, 500, 1000, 2000, 4000, 8000):
    while bf.count < target:
        bf.add(f"user-{bf.count}")
    fp = sum(bf.might_contain(x) for x in never_added) / len(never_added)
    ones = sum(bin(b).count("1") for b in bf.bits) / bf.m
    print(f"{bf.count:>12,} {ones:>8.0%} {fp:>15.2%}")

print("false negatives:", sum(not bf.might_contain(f"user-{i}") for i in range(bf.count)))

In the interview

Extra depth · not in the video
What to say when a lookup is expensive and most answers are “no”

“Most of these checks will come back ‘not seen’, so I’d put a Bloom filter in front. It’s a bit array of about 10 bits per item, which gives roughly 1% false positives: it can say ‘maybe’ for something that isn’t there, but it never says ‘no’ for something that is. For this use case a wrong ‘maybe’ only costs us one skipped item, so we never need to verify it. I’d keep one filter per user in Redis, sized for a few thousand items, monitor the fill level, and rebuild it from the database when it gets full, since a Bloom filter can’t be grown or have items removed.”

A worked design question

“Design the ‘never show a post the user has already seen’ feature for a feed with 500 million users.” Walk it in the lesson’s order: numbers, then the picture, then the trade-offs.

1 · Numbers

Per user, then total

  • Keep the last ~5,000 seen posts per user. At 10 bits each: ~6 KB per filter.
  • 500M users × 6 KB = 3 TB. Too much to keep hot for everyone.
  • But only ~50M are active on a given day: 50M × 6 KB = 300 GB. That fits a Redis cluster of 10–15 nodes.
2 · The read path

One round trip per feed

  • Feed service ranks ~1,000 candidate posts.
  • One BF.MEXISTS seen:{uid} … call checks all 1,000 at once.
  • Drop every “maybe”. Serve the rest. The user never sees a repeat.
3 · The write path

Two writes per view

  • On “post shown”: BF.ADD seen:{uid} post and append to the views table in the database.
  • The database is the truth; the filter is rebuilt from it if lost or full.
4 · Trade-offs to name

Say them before being asked

  • 1% of fresh posts are wrongly skipped. Acceptable; tune p if not.
  • Filters of inactive users expire from Redis and are rebuilt from the database on their next visit.
  • A full filter means an empty feed, so alert on fill level and rotate (section 7.3).

Likely follow-ups. Answer each out loud before opening it.

What is a Bloom filter, in two sentences?

A bit array plus a few hash functions that remembers whether items were added without storing the items. It answers “definitely not in the set” or “probably in the set”, never a false “no”, but sometimes a false “yes”.

Why can it never give a false negative?

Adding an item sets all k of its bits to 1, and bits are never cleared. So any item that was added still has all its bits set, and a check on it must return “yes”.

The only ways to break this are to clear bits (deletes) or to rebuild the filter from an incomplete list, which is why you rebuild from the source of truth.

Why can you not delete from it?

Bits are shared. In the lesson, apple and cat both set bit 2. Clearing bit 2 to remove cat would also make apple disappear, and that is a false negative, the one thing the structure promises never to do.

If you need deletes, use a counting Bloom filter (counters instead of bits, about 4× the memory) or a cuckoo filter.

How do you size it?

From two inputs: how many items you will insert, and the false positive rate you accept. About 10 bits per item gives 1%; about 15 gives 0.1%. The optimal number of hash functions is around 0.7 × bits-per-item, so 7 for 1%.

Then over-provision, because the rate climbs steeply past the designed capacity and the filter cannot be grown.

Why not just one hash function, like the lesson’s example?

With one hash, a stranger is wrongly accepted whenever its single bit is set, so the false positive rate equals the fraction of bits set, which is high.

With k hashes a stranger must hit k set bits at once, which is far less likely. At the same memory, 7 hashes turn a ~50% error rate into ~1%.

What happens when it fills up, and how do you handle it?

It does not fail, it degrades: more and more “maybe” answers. In front of a database that means more real lookups; in a recommender it means fewer and eventually zero recommendations.

Handle it by monitoring the fill level, over-provisioning, and rotating: build a larger filter from the source of truth, add new items to both during the build, then swap atomically.

Where would you put it: in the service or in Redis?

In the service’s memory when the data changes slowly and every server can hold its own copy: it is nanoseconds per check. In Redis when the data changes constantly or must be shared, such as per-user “seen” sets: one copy, every server sees every add, and it survives deploys, for one network round trip.

Name three real systems that use one.

Cassandra, HBase and RocksDB keep a filter per data file so a read opens only the files that might contain the key. Akamai’s CDN caches an object only on its second request, using a filter to spot the first. Medium and Instagram-style feeds use per-user filters to avoid showing the same content twice.

Bloom filter, bitmap or set: which when?

Bitmap when the keys are dense integers in a known range, such as user IDs: one bit per ID, exact, deletable. Set when you need exact answers and listing and can pay the memory. Bloom filter when the keys are arbitrary (URLs, strings), the count is huge, and a small false positive rate is acceptable.

Is the Bloom filter a source of truth?

Never. It cannot even list its contents. The real list lives in a database; the filter is a fast, approximate copy of one fact about that list. Losing it costs a rebuild, not data.
