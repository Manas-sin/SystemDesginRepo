Design an E-commerce Product Listing

The first full design problem in the course, kept deliberately small: one shop, a hundred products, lots of visitors. The point is not the shop. It is watching every box get a reason before it is drawn. These notes follow that walk, then add the numbers, the schema, the API and the follow-ups an interviewer will push on.

19 min 39 s video Blue sections · from the video Amber sections · extra depth

The whole lesson in six lines

  1. The problem: one shop owner, at most 100 products, hundreds of thousands of visitors. The owner can add, update, delete and list products; customers browse the catalog. No payments.
  2. Storage first, with arithmetic: 100 items × 1 KB = 100 KB. That fits on any single node. The data is structured (title, description, colour, price), so a relational database.
  3. Access over HTTP: API servers, more than one, so a load balancer in front. Users → load balancer → API servers → database. The classic three tiers.
  4. Two front ends, one backend: a customer-facing catalog frontend and a separate admin UI for the owner, both calling the same backend, which checks the admin role on every write.
  5. Load per piece: frontend and backend scale out behind their load balancers with autoscaling; the admin UI has one user and needs one server (plus a spare); the database is the read-heavy piece.
  6. Scale reads with replicas, not a cache: each API server opens two connections and spreads reads over main and replica. Writes go to main and are copied to replicas, so there is nothing to invalidate. “The main only takes writes” is a myth.

1

The problem, and why it is kept small

From the video▶ 0:00

A small shop owner has about a hundred items and wants them listed on a website. Hundreds of thousands of people will visit. That is the whole brief.

The lesson is explicit about its motive: every design has one, and here it is to practise a structured approach. Small steps, not big leaps. Each piece of infrastructure gets added only when something forces it, so you learn what each piece is for.

Features ▶ 0:57

Shop owner

Manage the catalog

  • Add a new product
  • Update or delete an existing product
  • List all products
Customer

Browse the catalog

  • Open the site and see the products
  • Read only, nothing is written
Out of scope, on purpose

No payments, no cart, no orders. The lesson says later why it drew the line here: with no customer writes, the traffic is almost purely read-heavy, and that one property drives the biggest decision in the design.

2

Storage: estimate, then pick

From the video▶ 1:20

The lesson starts with storage because it is the easiest piece to reason about. “The data is small and fits on a single node” is a general statement; the lesson insists on backing it with a number.

one product (title, description, colour, …) ≈ 1 KB
100 products × 1 KB = 100 KB
→ fits on the smallest database server you can rent

Which database? ▶ 2:12

When data is this small, almost any database would work and the choice would not matter much. So decide on shape, not size. A product has a clear structure: title, description, colours, a price, maybe a few reviews. Structured rows with a fixed schema are what a relational (SQL) database is for, and there is no reason to go for anything fancier.

Decision 1

A relational database with a products table. Justified by the size (tiny) and the shape (structured). Section 7.2 writes the actual schema.

3

Access: HTTP, API servers, a load balancer

From the video▶ 2:56

The catalog is reached over the internet, so the protocol is HTTP: every browser, phone and client library speaks it (lesson 21). So: an HTTP server that exposes a few APIs over the database.

One server may not handle the traffic of a popular listing, so run several. The moment you have more than one server you need a load balancer: the single address every client talks to, which spreads requests across the servers. Give it a domain name, say api.mystore.com.

What you have now is the three-tier architecture: users, compute, storage.

Name the pieces: the catalog backend service (the APIs) and the catalog database (the data). Two boxes. That is the whole system so far.

4

A frontend for customers, an admin UI for the owner

From the video▶ 5:40

Customers do not make JSON calls. They need pages. So add a catalog frontend service: the customer talks to the frontend, the frontend calls the backend’s APIs, the backend reads the database. The classic way to build an application.

The owner needs something different: a place to add products and edit titles and descriptions. That is a second frontend, the admin UI. It calls the same backend, using the create, update and delete APIs.

Where is the browser? It is the Customers box, and the owner box is their browser too. The word “frontend” trips people up here: in this drawing, catalog frontend is not the browser. It is a set of servers behind a load balancer whose only job is to hand pages to the browser. The chain is browser → frontend servers → backend API → database.

The lesson draws the classic style, where the frontend server builds the page and calls the backend itself. In a React-style app the frontend servers hand over the JS bundle once, and after that the browser calls the backend API directly. Same boxes, one extra arrow from the browser to the backend, and the frontend box shrinks to a static-file host or CDN.

Why a separate admin UI? ▶ 7:02

Both are “just frontends”, and an early startup often ships them as one app. The lesson still separates them, for two reasons:

  • Different jobs, different code. The admin screens look nothing like the shop. If the two code bases tangle, a bug in one breaks the other.
  • Admin is a superpower. If the admin screens ship inside the public frontend, anyone can read that code, find the admin API calls, and start poking at them. Keeping the admin frontend separate keeps it out of every customer’s browser.

A common backend is fine. The rule there is simple: on every API call, check whether the caller has admin privileges. If yes, writes are allowed. If not, reads only.

Load on each piece

From the video▶ 8:32

Four components now: frontend, admin UI, backend, database. The lesson walks them one by one and asks of each: how much traffic, and what do we do about it?

Autoscaling does the adding for you ▶ 10:05

Every cloud has a way to say “behind this load balancer there must always be at least N healthy servers, and up to M when busy”. In AWS that is a target group with an autoscaling policy. If a server dies, a new one is started without anyone being paged. For the admin UI, N is 1: the cloud guarantees one server is always up. For the frontend and backend, the policy scales on incoming requests.

This is the practical form of lessons 19 and 20: stateless servers are replaceable, and the replacing is automated.

6

Scaling the database: replicas, not a cache

From the video▶ 11:18

There are no payments, so no customer ever writes. The only writes come from one owner editing a hundred items: a few per day. Everything else is reads. The lesson chose the constraint to make this obvious: the traffic is read-heavy.

If one database cannot keep up with the reads, add a read replica: a second database that receives a copy of every write and can serve reads. Then change the backend so it sends some reads to the main and some to the replica.

Busting a myth ▶ 12:26

“But the main only handles writes!” No. That is not a rule. The main can serve reads as well, as long as that fits your system. Here the writes are minuscule, so the main has plenty of room to serve reads too. Main: reads and writes. Replica: reads.

How the backend spreads reads ▶ 13:49

Every API server opens two database connections when it starts: one to the main, one to the replica. For each read it picks one of the two, at random. Writes always use the main connection. Need more read capacity? Add a third database and a third connection. Nothing stops you.

“Why not just add a cache?” ▶ 15:20

You could. There is nothing wrong with a cache in front of the database, and it is the more common answer. The lesson chose replicas on purpose, and gives its reason:

With a cache

You own invalidation

The cache holds a copy of a product. The owner edits that product. Now the cache is wrong, and your code must delete or update that key on every write, or customers see stale data.

With replicas

Replication does it for you

The owner’s write lands on the main and is copied to every replica by the database itself. No key to delete, no stale copy to think about. Reads still scale: add replicas as needed.

The lesson’s real point ▶ 16:34

Every box got a justification. Two options were on the table to scale reads; one was chosen for a stated reason that fits this system (rare, tiny writes). “Just because a cache exists does not mean you add it.” That habit, a reason for every box, is what the interviewer is grading.

7

Going deeper

Extra depth · not in the video

The lesson does the storage estimate but not the traffic one, names the APIs but does not write them, and skips the one thing that bites every read-replica setup. Here is the rest, in the order of the 7-step route.

7.1 · The traffic estimate the lesson skipped

“Hundreds of thousands of visitors” is not a number yet. Pick one and say your assumption out loud:

200,000 visitors/day × 10 pages each = 2M page views/day
each page = 1 HTML + 3 API calls (list, categories, shop info) = 4 requests
2M page views × 4 = 8M requests/day
8M ÷ 86,400 s ≈ 95 requests/s average · peak 3× ≈ 300/s
API calls = 2M × 3 = 6M/day; categories and shop info rarely change, so not every call reads the DB → 2–3M DB reads/day ≈ 30/s

Every number here is an assumption, and that is fine. 10 pages per visit and 3 API calls per page are guesses you say out loud; the interviewer can swap them and the arithmetic still works.

Now the honest conclusion: a single modest API server handles a few thousand simple requests per second, and a single database handles tens of thousands of simple reads per second. At this scale one of each would do. The lesson over-provisions on purpose, to show you the pieces. What you should take from it is the order in which you add them as traffic grows, and roughly when:

TrafficComputeDataWhy
up to ~1,000 req/s2 small API servers behind a load balancer1 database + 1 standbythe second server and the standby are for availability, not load (lesson 19)
~1,000 – 10,000 req/sautoscaling groupmain + 1–2 read replicas; images on S3 behind a CDNreads outgrow one database; images are most of the bytes (lesson 22)
~10,000 – 100,000 req/sautoscaling, many serverscache (Redis) for product reads; CDN caching of the listing itself with a short TTLreplicas cost a database server each; a cache serves a read for a fraction of the cost
beyondsplit by shopshard the database by shop (lesson 24); search in a separate indexone database can no longer hold or serve the whole catalog

7.2 · The schema (the lesson’s exercise asks you to write it)

CREATE TABLE products (
  id           BIGSERIAL PRIMARY KEY,
  title        TEXT        NOT NULL,
  description  TEXT,
  color        TEXT,
  price_cents  INTEGER     NOT NULL CHECK (price_cents >= 0),  -- never store money as a float
  currency     CHAR(3)     NOT NULL DEFAULT 'INR',
  stock        INTEGER     NOT NULL DEFAULT 0,
  status       TEXT        NOT NULL DEFAULT 'active',           -- active | hidden | deleted
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE product_images (
  product_id   BIGINT   NOT NULL REFERENCES products(id),
  position     SMALLINT NOT NULL,
  url          TEXT     NOT NULL,                                -- an S3 key served through the CDN (lesson 22)
  PRIMARY KEY (product_id, position)
);

CREATE INDEX products_listing_idx ON products (status, id);     -- the listing query: WHERE status='active' ORDER BY id
  • Soft delete. “Delete” sets status = 'deleted'. The owner can undo it, and old orders (when you add them) still point at a real row.
  • Images are not in the database. They are bytes; bytes go to blob storage. The table keeps the key. This is the single biggest thing the lesson leaves out, because images will be 99% of the bandwidth of a shop.
  • One index, for the one query customers run. Do not index what you do not query.

7.3 · The API

EndpointWhoNotes
GET /products?limit=20&cursor=…anyonethe listing. Cursor pagination (“rows after id 40”) rather than page numbers: it stays fast and does not skip or repeat rows when the owner edits mid-scroll.
GET /products/{id}anyoneone product with its images.
POST /productsadmincreate. Body is validated (price ≥ 0, title non-empty).
PUT /products/{id}adminupdate. Bumps updated_at.
DELETE /products/{id}adminsoft delete.

“Admin” is a role carried in the owner’s login token (a signed JWT or a server-side session). One middleware in the backend checks it before any write handler runs. The frontend never decides who is admin; it only shows or hides buttons.

7.4 · The catch with replicas: replication lag

Replication is usually asynchronous: the main confirms the write, then ships it to the replicas a moment later. Usually that moment is milliseconds. Under load it can be seconds. During that moment the replica is behind, and a read that lands on it returns the old row.

For customers that is harmless: a title that is a second old is still a title. For the owner it is a bug report: they hit Save, the page reloads, and the old title is still there, because that read happened to go to the replica. The lab in section 8 reproduces this exactly.

Three standard fixes, cheapest first:

Fix 1 · route by caller

Admin reads main

Requests carrying the admin role use the main connection for reads too. The owner always sees their own writes; customers keep using replicas. One if in the backend.

Fix 2 · route by recency

Read main after a write

After any write, send that user’s reads to the main for a few seconds (store a timestamp in their session). Called read-your-writes. Works when customers also write.

Fix 3 · change replication

Synchronous replica

The main waits for the replica to confirm before answering. No lag, but every write is slower and a slow replica slows the main. Usually overkill for a catalog.

7.5 · Replica vs cache, the full comparison

The lesson gives one reason (invalidation). An interviewer will want the whole trade.

Read replicasCache (Redis)
Freshnessautomatic: replication carries every write. Lag of ms–s.your job: delete or update the key on every write, or accept a TTL’s worth of staleness.
Speed per reada normal database query, ~1–5 ms.~0.2 ms, and no SQL work at all.
Cost per reada database server per replica; a replica holds all the data even if 1% is hot.cheap; holds only the hot 1%. One Redis node absorbs what would take many replicas.
Failurea replica dies → the others carry on, slightly busier.the cache dies → every read hits the database at once (a “thundering herd”). Needs warming and care.
Can doany query, including ones nobody thought to cache.only what was cached, keyed exactly.
Pick it whenwrites are rare and small, reads are varied, data is small, you want correctness with no extra code. This lesson.reads are enormous and repetitive (the same 1,000 hot products), latency matters, you can handle invalidation.

They also combine. Many shops run both: a cache for the hottest reads, replicas behind it for everything else and for availability. And a CDN in front of all of it for the images and, with a short TTL, the listing page itself.

7.7 · Limits worth saying out loud

  • One region. Everything sits in one data centre. A regional outage takes the shop down. Backups in a second region first; a second deployment later.
  • The main is still a single point of failure until a standby and failover exist. Replicas scale reads; they do not by themselves make writes available.
  • Replicas are eventually consistent. Fine for a catalog, wrong for stock counts and payments.
  • “Autoscaling” scales stateless servers only. Nothing autoscales the database; that is the part you design by hand, which is why the lesson spends its last eight minutes there.
8

Hands-on lab

Exercise from the video▶ 17:34 · code added here

The lesson’s exercise: design the table, stuff it with 100 generated products, write a backend with two database connections that alternates reads between main and replica, set up replication, change one row on the main and watch it appear on the replica. Then, as a stretch, add a cache and feel the invalidation problem.

Below is a version you can run in ten seconds with nothing installed: two SQLite files play main and replica, and a tiny background thread plays the replication, with a deliberate half-second lag so you can see it. Step 4 has the real-Postgres version.

  1. Save this as catalog.py

    Schema, 100 generated products, an asynchronous replicator, and a backend that holds two connections and picks one at random per read.

    import random, sqlite3, threading, time

SCHEMA = """
CREATE TABLE IF NOT EXISTS products (
  id          INTEGER PRIMARY KEY,
  title       TEXT NOT NULL,
  description TEXT,
  color       TEXT,
  price_cents INTEGER NOT NULL,
  stock       INTEGER NOT NULL DEFAULT 0,
  updated_at  REAL NOT NULL          -- used by the replicator to find changed rows
);"""

def connect(path):
    c = sqlite3.connect(path, check_same_thread=False, isolation_level=None)
    c.execute(SCHEMA)
    return c

main, replica = connect("main.db"), connect("replica.db")

# --- the shop owner's 100 items --------------------------------------------
random.seed(26)
nouns, colors = ["Mug", "Lamp", "Scarf", "Notebook", "Bottle", "Chair", "Poster", "Candle"], ["red", "blue", "green", "black"]
main.execute("DELETE FROM products")
for i in range(1, 101):
    main.execute("INSERT INTO products VALUES (?,?,?,?,?,?,?)",
                 (i, f"{random.choice(colors).title()} {random.choice(nouns)} #{i}", "lorem ipsum " * 40,
                  random.choice(colors), random.randint(199, 9999), random.randint(0, 50), time.time()))

# --- an asynchronous replica: copies changed rows from main every 0.5 s -----
def replicate_forever(lag=0.5):
    seen = 0.0
    while True:
        rows = main.execute("SELECT * FROM products WHERE updated_at > ?", (seen,)).fetchall()
        for r in rows:
            replica.execute("INSERT OR REPLACE INTO products VALUES (?,?,?,?,?,?,?)", r)
            seen = max(seen, r[6])
        time.sleep(lag)
threading.Thread(target=replicate_forever, daemon=True).start()
time.sleep(1)   # let the first copy land

# --- the backend: two connections, reads spread at random, writes to main ---
class Backend:
    def __init__(self):
        self.pool = {"main": main, "replica": replica}
        self.reads = {"main": 0, "replica": 0}
    def get_product(self, pid):
        name = random.choice(list(self.pool))                 # the lesson's "pick one at random"
        self.reads[name] += 1
        return self.pool[name].execute("SELECT title FROM products WHERE id=?", (pid,)).fetchone()[0]
    def list_products(self):
        return self.pool["replica"].execute("SELECT id, title, price_cents FROM products ORDER BY id LIMIT 3").fetchall()
    def update_title(self, pid, title):                       # admin only; always the main
        main.execute("UPDATE products SET title=?, updated_at=? WHERE id=?", (title, time.time(), pid))

api = Backend()
print("first 3 products (from replica):", api.list_products())
for _ in range(1000):
    api.get_product(random.randint(1, 100))
print("1000 reads spread over:", api.reads)

api.update_title(7, "Blue Mug #7 — SALE")
print("right after the admin write:   main =", main.execute("SELECT title FROM products WHERE id=7").fetchone()[0],
      "| replica =", replica.execute("SELECT title FROM products WHERE id=7").fetchone()[0])
time.sleep(1)
print("one second later:              main =", main.execute("SELECT title FROM products WHERE id=7").fetchone()[0],
      "| replica =", replica.execute("SELECT title FROM products WHERE id=7").fetchone()[0])

    Reads split roughly half and half with no code beyond random.choice. The admin write went to the main only. Immediately after it, the replica still had the old title: that is replication lag (section 7.4), and a customer reading at that instant would see “Red Mug”. One second later both agree, and nobody invalidated anything.

Try next (the lesson’s stretch)

Add a cache: a plain Python dict in get_product that stores titles by id. Update a title and read it again: the dict still returns the old one, and it never recovers until you delete that key in update_title. That is cache invalidation, and that is why the lesson chose replicas. Then add fix 1 from section 7.4: give get_product an is_admin flag that forces the main connection, and the stale read disappears for the owner.

9

In the interview

Extra depth · not in the video
What to say, in the lesson’s order

“Let me estimate first: a hundred products at a kilobyte each is a hundred kilobytes, so storage is trivial and I’ll use a relational database because the data is structured. The traffic is read-heavy: customers only read, one owner writes a few times a day. So: a customer frontend and a separate admin UI, both calling one stateless backend behind a load balancer with autoscaling. To scale reads I’d add read replicas and have each API server hold two connections and spread reads across them. I’m choosing replicas over a cache because writes are so rare that replication keeps every copy fresh for free, whereas a cache would need invalidation code. I’d route the owner’s own reads to the main so they never see a stale edit, put images in S3 behind a CDN, and add a cache only when replicas stop being the cheap answer.”

The follow-up they will ask: “now make it a marketplace”

“Ten thousand shops, ten million products, fifty million page views a day. What changes?” Same route: numbers, then the picture, then what you would add.

1 · Numbers

Most of it still fits

  • 10M products × 1 KB = 10 GB of rows. Still one database.
  • 10M products × 4 photos × 300 KB = 12 TB of images. Not the database: S3 + CDN.
  • 50M views/day ≈ 580 req/s average, ~2,000/s peak, ×4 API calls per page ≈ 8,000/s. Autoscaling handles it.
  • Writes: 10,000 owners × a few edits/day. Still tiny.
2 · What stays

The whole shape

  • Two front ends, one backend, autoscaled.
  • One relational main with replicas; writes are still rare.
  • Add a shop_id column and index to every table; every query filters by it.
3 · What you add

Three new boxes

  • CDN + S3 for images (99% of the bytes).
  • Cache for hot products and shop pages, invalidated on write; CDN caches listing JSON for 30 s.
  • Search index (Elasticsearch) fed from the database, because “red mug under ₹500” is not a job for LIKE.
4 · Trade-offs to name

Say them before being asked

  • A famous shop is a hot key: its reads all hit one place. The cache absorbs it.
  • Cache and search index are copies: both can be seconds behind. Fine for a catalog, never for stock or money.
  • If one database ever is not enough, shard by shop_id on a hash ring (lesson 24): a shop never spans two shards.

Likely follow-ups. Answer each out loud before opening it.

Why a relational database and not NoSQL?

The data is tiny (100 KB) and structured: every product has the same fields. A relational table fits that shape exactly, gives you constraints and indexes for free, and there is no scale argument for anything else. Pick the database for the shape of the data; size only matters once it is large.

When do you need a load balancer?

The moment you have more than one server for the same job. It is the single address clients talk to and it spreads requests across the servers. It is so universal that the lesson stops drawing it: a service box means “load balancer plus stateless servers”.

Why a separate admin UI? It is just another frontend.

Two reasons: the admin screens are different code with different bugs, and admin is a superpower. Shipping admin screens inside the public frontend puts the admin API calls in every customer’s browser. A separate frontend keeps them out of sight. The backend still checks the role on every write, because the frontend is never the security boundary.

Why read replicas instead of a cache?

Because writes are rare and tiny, replication keeps every copy fresh with no code. A cache would need invalidation on every edit. The lesson’s honesty: both are valid, it chose the one that needs no extra correctness work for this system.

Flip the choice when reads become enormous and repetitive: a cache then serves the hot products for a fraction of the cost of another database server.

Can the main database serve reads?

Yes. “Main only takes writes” is a habit, not a rule. Here the writes are a handful a day, so the main has almost all its capacity free for reads. Which connection a read uses is a decision in your backend code, nothing more.

How does the backend decide where a read goes?

Each API server opens one connection per database at start-up. For a read it picks one at random (or round robin, or weighted). For a write it always uses the main. Adding a replica is adding a connection.

What goes wrong with read replicas?

Replication lag. Replicas are a little behind the main, so a read just after a write can return the old row. The owner hits Save, reloads, and sees the old title.

Fix: route the admin’s reads to the main, or route any user’s reads to the main for a few seconds after they write. Synchronous replication removes the lag but slows every write.

What happens if the main database dies?

Reads keep working from the replicas; writes stop until a replica is promoted to be the new main (failover, lesson 19). A read replica can double as the standby for this, which is one more reason to have one even at small scale.

Where do the product images go?

Not in the database. Bytes go to blob storage (S3), the table keeps the key, a CDN serves them near the user, and the owner uploads straight to S3 with a pre-signed URL so the bytes never pass through the API servers (lesson 22). Images will be nearly all of the bandwidth of a shop.

How do you paginate the listing?

With a cursor (“give me 20 rows after id 40”) rather than page numbers. Offset pagination gets slower as the offset grows and skips or repeats rows when the owner edits between page loads. A cursor on an indexed column is constant time and stable.

Isn’t this over-engineered for one shop?

Yes, and say so. At a few hundred requests per second one API server and one database would cope. The lesson adds each piece to teach what it is for. In the interview, do the estimate, state that one of each would do, then explain which piece you would add first (a second server and a standby, for availability) and at what traffic the replicas and then a cache become necessary.

How would you support 10,000 shops?

A shop_id column on every table, indexed, with every query filtering by it: 10 million products are still only 10 GB. Images to S3 and a CDN, a cache for hot shops, a search index. Only if one database cannot hold or serve it all, shard by shop_id on a consistent-hashing ring so a shop never spans two shards.
