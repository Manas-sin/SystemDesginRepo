Blob Storage & S3

Where do the photos, videos and backups go? Not in the database, and not on the API server’s disk. These notes cover what the lesson says about blob storage, then go deeper on the parts an interviewer will push on.

15 min 31 s video Blue sections · from the video Amber sections · extra depth

The whole lesson in six lines

  1. A blob is any file, treated as a plain run of bytes. Blob storage keeps those bytes and gives them back. It never looks inside.
  2. In the early days, an uploaded file was saved on the hard disk of the one server that received it — the “static folder.”
  3. That breaks as soon as you have several servers: the file sits on one server’s disk, and the next request may land on a different server.
  4. The fix is one shared store on the network that every server can reach. On AWS that store is S3. The API servers keep no files, so they are stateless again.
  5. In S3 a file lives in a bucket (a named container) under a key (a path-like name). You can create, replace, delete, and read all or part of a file.
  6. S3 is cheap, durable and effectively unlimited. In exchange, reads are slower than a local disk, and it is not a real file system.

1

What a blob is

From the video▶ 0:00

Blob stands for binary large object. In practice it means any file: a photo, a video, a PDF, even a text file. To a computer every file is just a long run of bytes.

Blob storage is a place that stores those bytes and hands them back when asked. It does not open the file or try to understand it. There is no required format, no schema (a fixed list of columns, like a database table has), and no rules about what is inside. Any bytes in, the same bytes out.

The most widely used blob storage in the world is S3, a managed service from AWS. “Managed” means AWS runs the machines and you just call it. You will see S3 in almost every system design, so it is worth knowing what it does and why it exists.

Key idea

A database understands your data: rows, columns, queries. Blob storage does not. It is a giant shelf where you put a box under a label and later ask for the box by that label.

2

The old way: files on the server’s own disk

From the video▶ 1:12

S3 has not been around forever. To see why it was needed, look at how file uploads worked on the early internet.

Traffic was small, so one server did everything. That server had a hard disk attached, the same way your laptop has one. When a user uploaded a file, the server simply saved it on that disk.

How the “static folder” worked ▶ 2:12

The server exposed an endpoint (a URL that accepts requests) for uploads. It also had one special folder on its disk, usually called the static folder, at a fixed, hand-written location. If you have built a small web app you have probably seen a folder named static. This is its job.

Both directions are the same trick: glue the folder’s location and the file name together to get a full path on the disk.

# the one folder on this server's disk that holds uploaded files
STATIC_DIR = "/home/app/www/static"

# upload: the file arrives in the body of an HTTP POST request
POST /upload            (file name: a.txt)
  path = STATIC_DIR + "/" + "a.txt"      # /home/app/www/static/a.txt
  write the request body to path

# download: the user asks for /static/a.txt
GET /static/a.txt
  path = STATIC_DIR + "/" + "a.txt"      # the same path again
  read the file at path and send it back

That full path is the file’s identity. Image uploads, text file uploads, everything worked this way, and many small systems still do. It is also all you need to write your own static file server.

3

Why that breaks with more than one server

From the video▶ 4:41

This worked well for a long time. It stops working the moment you add a second server, because each server has its own disk.

You could try to patch this. One patch is a sticky load balancer: one that always sends the same user to the same server. But that only piles on problems. Other users still cannot see the file, the file dies with that one server, and a single disk can only grow so big.

The lesson’s point: do not go down that road. The disk itself is in the wrong place.

The two real problems

Routing: with files spread over many private disks, no request knows where to go. Size: the data keeps growing, and one machine’s disk does not.

4

The fix: one shared store every server can reach

From the video▶ 5:11

What you actually need is storage that is attached to the network instead of to one machine, and that never fills up. The lesson’s phrase is an “infinitely scalable, network-attached storage.” That is what S3 is, and that is what blob storage means in practice.

Now servers stop saving files on their own disks. They save them remotely, in S3.

The upload path now

  1. The user uploads a file. The request reaches the load balancer.
  2. The load balancer forwards it to any API server.
  3. That API server stores the file in S3 and waits for S3 to confirm.
  4. The API server tells the user “saved.”

Reading works from any server too. Whichever one gets the request asks S3 for the file and passes it back to the user.

Why this matters

The API servers are stateless again: they hold no data of their own, so any of them can handle any request, and you can add or remove servers freely. All the “remembered” data lives in one shared place.

S3 offers a small set of simple operations — store a file, get a file, delete a file — so you do not have to build any of this yourself. It has become the default answer: if you are saving a binary file, it goes to S3.

5

Buckets and keys

From the video▶ 6:50

S3 has two names you need to know.

Bucket

A named container for files

You create a bucket before you can store anything. Think of it as a namespace: a label that keeps your files apart from everyone else’s.

The name must be unique across the whole world. If someone already took todo-app, you pick another name. Examples: insta-images, my-bucket.

Key

The file’s name inside the bucket

A key looks like a folder path, for example user123/72896.png. It is the label you store a file under and ask for it by.

Inside, S3 stores things differently from real folders. You do not need to care: to you a key is just a path.

s3:// insta-imagesbucket / user123/72896.pngkey

The lesson’s example. You are building Instagram. User 123 uploads an image named 72896.png. Your API server receives the image over HTTP, then makes one S3 call: store these bytes in bucket insta-images under key user123/72896.png.

It is the same idea as the static folder. Back then you built a path on the local disk. Now you build a path (the key) in S3. The call is made with the AWS SDK, a code library AWS gives you for talking to its services.

What you can do with a file ▶ 8:27

  • Create a file.
  • Replace a file with a new one.
  • Delete a file.
  • Read the whole file in one go, or read just a segment of it.

That list is short on purpose. Notice what is missing: there is no “open the file and change the middle of it.” This is why the lesson says S3 is not a full-fledged file system. Section 7.2 explains what that costs you.

Who can read your files ▶ 9:16

S3 has security policies. Nobody else can read your files unless you give them access, and you cannot read another customer’s files unless they give access to you.

6

Strengths, weaknesses, and when to use it

From the video▶ 8:40

Most teams treat S3 as a black box: put files in, get files out, pay for what you store and how often you access it. Here is what you get and what you give up.

Advantages
  • Cheap and durable. Storage costs little, and S3 keeps several copies of every file so it does not get lost. (Durable = your data survives.)
  • Stores literally any file. Images, video, audio, text, database backups, CSV exports.
  • Scalable and available. It never fills up, it handles many requests at once, and it is almost always reachable.
  • Plugs into everything. Other AWS services, and big-data tools such as Apache Spark and Kafka, can read from and write to S3 directly.
Disadvantages
  • Reads are slow. A disk (SSD or HDD) attached straight to your machine is much, much faster. If you need very quick reads, do not use S3; use the local disk.
  • Not a full-fledged file system. You cannot use the normal “open, read, write” file commands of your operating system. You must go through the AWS SDK or S3’s API calls.
A number to double-check

Around 10:02 the lesson quotes a figure with a long row of nines and calls it availability. The famous S3 number is about durability, not availability. Section 7.1 gives both numbers and the difference.

Why big-data tools love it ▶ 10:11

Big-data work means processing huge amounts of data. That data has to sit somewhere that never runs out of space. S3 is exactly that, so nearly every big-data tool can read, write and crunch data in S3 without extra plumbing. This is a large part of why “S3” and “blob storage” are used almost as the same word.

When to use S3 ▶ 11:57

Use it when you want to store a blob that needs to be reachable from one central place. The lesson lists five common uses:

UseWhy S3 fits
Database backupsLarge files, written once, rarely read, must not be lost
Log archivesOld logs pile up forever and are almost never opened
Static website hostingHTML, CSS, JavaScript and images are just files to hand out
Big-data storageNeeds unlimited space, and the tools already speak S3
A dumping ground for rarely used dataCheap to keep around “just in case”

The “why” column is a short reading of the lesson’s list, not a quote.

It is not only S3 ▶ 14:46

Google Cloud Storage and Azure’s blob storage are very similar. If you understand S3, you understand them. If you are not on a cloud at all, the lesson points to HDFS (the storage layer of the Hadoop big-data system) as the equivalent you run yourself.

7

Going deeper

Extra depth · not in the video

The lesson stops at section 6. These are the follow-up questions an interviewer is likely to ask next.

7.1 · Durable and available are two different promises

  • Durability: will my file still exist? S3’s standard class is designed for 99.999999999% durability — eleven nines. AWS’s own illustration: store ten million files and you should expect to lose one about every ten thousand years.
  • Availability: can I reach my file right now? The standard class is designed for 99.99%. That allows roughly 53 minutes a year when requests may fail.

So a file can be perfectly safe and still be unreachable for a few minutes. Losing data and being unable to reach it for a moment are very different failures, which is why they get separate numbers.

How does it get eleven nines? Each file is spread across many disks in at least three separate data centres (AWS calls them availability zones). S3 keeps checking the stored pieces for damage and quietly repairs them from the healthy ones. To lose a file, many disks in different buildings would have to fail at almost the same time.

7.2 · Three kinds of storage, and why S3 is “not a file system”

Cloud storage comes in three shapes. They are easy to mix up, and interviewers like to check that you can tell them apart.

Concretely, “not a file system” means:

  • No editing in place. To change one byte of a 1 GB file, you upload 1 GB again. There is no “append a line to the end” either.
  • No real folders. A key such as user123/72896.png is one long name that happens to contain a slash. “List the folder user123/” really means “list every key that starts with user123/.”
  • No rename. Renaming is done as copy to the new key, then delete the old one.

Giving up these features is the trade that buys unlimited size. A simple “label → whole file” model is far easier to spread over thousands of machines than a tree of folders that many programs are editing at once.

7.3 · Why reads are slow, and what to do about it

Every S3 read is a web request that travels over the network to another machine. It typically takes tens to a few hundred milliseconds before the first byte comes back. A read from a disk attached to your own machine takes well under a millisecond.

Once a download has started, S3 moves bytes quickly. So it is fine for big files and bad for workloads that make thousands of tiny reads and need each one instantly. That is why a database keeps its data on an attached disk, not in S3.

For files shown to users, the fix is a CDN (content delivery network): a fleet of servers around the world that keep copies of your files close to users. The first request for a photo goes to S3. After that the CDN answers from its nearby copy, and S3 is not involved.

7.4 · Do not push the file through your API server

In the lesson the file travels user → API server → S3. That is the simplest picture, but for large files it wastes your servers: a 2 GB video ties up one server’s network and memory for minutes, just to pass bytes along.

The standard fix is a pre-signed URL. This is a temporary web address created by your server that allows one specific action (say, “upload to this exact key”) for a few minutes. Whoever holds the address can do that one thing and nothing else, with no AWS password needed.

7.5 · The file goes in S3; the facts about the file go in a database

S3 can fetch a file by its key, but it cannot answer questions like “show me all photos by user 123, newest first.” So you keep two things:

  • In S3: the bytes.
  • In a database row: the facts about the file (its metadata) — who owns it, its size, its type, when it was uploaded, whether the upload finished — plus the S3 key that points to the bytes.

Why not put the file itself in the database? A database is built for small rows that are searched and updated. Storing videos in it makes the database huge, makes backups and replicas slow, and uses its expensive fast disks for bytes that nobody ever queries.

7.6 · Choosing keys

  • Never use the user’s file name as the key. Two users will both upload photo.jpg, and the second upload silently replaces the first. Generate a unique ID for each file and keep the original name in the database.
  • Start keys with what you list by. You can only list by the beginning of a key. user123/… makes “all files for user 123” cheap.
  • Never build a disk path from user input. In the static-folder approach from section 2, a file name such as ../../etc/passwd can make the server read or overwrite files outside the folder. This attack is called path traversal.

S3 scales its speed by key prefix: each prefix can take at least 3,500 writes and 5,500 reads per second, and S3 adds capacity on its own as traffic grows.

7.7 · Big files: upload in parts, read in ranges

The lesson’s exercise asks how you would upload huge files and read a fragment of a file. These are the two answers.

  • Multipart upload. Cut the file into parts, upload the parts side by side, and S3 joins them at the end. If one part fails you resend only that part, not the whole file. A single plain upload is capped at 5 GB, so anything larger must use this. Each part is at least 5 MB (the last one can be smaller) and there can be up to 10,000 parts.
  • Range read. Ask for “bytes 1,000,000 to 2,000,000 only.” This is how a video player jumps to the middle of a film without downloading the start, and how a broken download resumes where it stopped.

7.8 · Is a file readable the moment it is written?

Yes. Since December 2020, S3 gives strong consistency: once an upload succeeds, the very next read or listing sees the new file. Older articles say S3 could briefly return the old version. That is no longer true.

7.9 · Keeping the bill and the mistakes under control

  • What you pay for. Three things: how much you store (roughly $0.023 per GB per month for the standard class in US regions), how many requests you make, and data sent out to the internet. That last one surprises people on apps that serve a lot of video.
  • Storage classes. Colder classes (Infrequent Access, then the Glacier archive classes) cost less to keep, but charge a fee per read, and the deepest archives take minutes to hours to bring a file back. They fit the lesson’s “rarely used data” and “log archive” cases.
  • Lifecycle rules. Instructions such as “after 30 days move to a colder class; after a year delete.” S3 applies them for you.
  • Versioning. When switched on, replacing or deleting a file keeps the old version, so a mistake can be undone.

7.10 · Security today

The lesson asks you to read about ACLs (access control lists: per-file lists of who may do what). Useful background, but note how things stand now:

  • New buckets are private by default, with a safety switch called Block Public Access turned on.
  • AWS now recommends leaving ACLs switched off and controlling access with policies instead: written rules attached to a bucket or to a user that say who may do what.
  • Files are encrypted on disk automatically.
  • To let one user see one private file, do not make it public. Hand them a short-lived pre-signed URL (7.4).

7.11 · Outside AWS

S3’s way of talking has become a shared standard. Other products accept the same calls, such as Cloudflare R2, or MinIO if you want to run blob storage on your own machines. Code written for S3 usually works with them after changing an address.

8

Hands-on lab

Exercise from the video▶ 13:28 · commands added here

The lesson ends with three tasks: read the S3 documentation and explore its API, read about ACLs, and, if you can, play with the API yourself. A free-tier AWS account is enough.

Here is one way to do the “play with it” part from a terminal. It uses the AWS command-line tool (aws), installed and logged in to your account. Replace YOUR-BUCKET with a name nobody else in the world has used. Allow about 15 minutes.

  1. Create a bucket

    If the name is taken you get an error. That is the “unique across the world” rule from section 5.

    aws s3 mb s3://YOUR-BUCKET
  2. Create a file under a key

    Everything after the bucket name is the key. No folder is created; user123/a.txt is one name.

    echo "hello blob storage" > a.txt
aws s3 cp a.txt s3://YOUR-BUCKET/user123/a.txt
  3. List by prefix, then read the whole file

    The first command lists every key that starts with user123/. The second prints the file to your screen.

    aws s3 ls s3://YOUR-BUCKET/user123/
aws s3 cp s3://YOUR-BUCKET/user123/a.txt -
  4. Read only a segment

    Ask for bytes 0 to 4. The file part.txt will contain just hello. This is the range read from section 7.7.

    aws s3api get-object --bucket YOUR-BUCKET --key user123/a.txt \
  --range bytes=0-4 part.txt
cat part.txt
  5. Replace the file

    Upload to the same key again. The old content is gone; there is no “edit.”

    echo "second version" > a.txt
aws s3 cp a.txt s3://YOUR-BUCKET/user123/a.txt
aws s3 cp s3://YOUR-BUCKET/user123/a.txt -
  6. See that it is private, then share it for five minutes

    The first command shows the Block Public Access switches. The second prints a pre-signed URL. Open it in a browser: it works. Remove everything after the ? and try again: access denied.

    aws s3api get-public-access-block --bucket YOUR-BUCKET
aws s3 presign s3://YOUR-BUCKET/user123/a.txt --expires-in 300
  7. Delete the file and the bucket

    A bucket must be empty before it can be removed.

    aws s3 rm s3://YOUR-BUCKET/user123/a.txt
aws s3 rb s3://YOUR-BUCKET
Try next

Upload a file of a few hundred MB with aws s3 cp and watch it: the tool switches to multipart upload on its own. Then find these in the docs, as the lesson asks: what the API calls PutObject, GetObject and DeleteObject take and return, and how ACLs differ from bucket policies.

9

In the interview

Extra depth · not in the video
What to say when the design has file uploads

“Files go to blob storage like S3, not to the database and not to the API servers’ disks, so the servers stay stateless. The database keeps one row per file with its owner, size, status and S3 key. For uploads, the client asks my API for a pre-signed URL and sends the bytes straight to S3, in parts if the file is large. For downloads I put a CDN in front, because S3 reads are slow and users are far away. Buckets stay private; access is through short-lived signed links.”

Likely follow-ups. Answer each out loud before opening it.

Why not just save uploads on the API server’s disk?

With more than one server, the file is on one server’s disk and the next request may hit another. The file is also lost if that server dies, and one disk cannot grow forever.

Putting files in a shared store keeps the servers stateless, so any server can handle any request and servers can be added or removed freely.

Why not store the images in the database?

Databases are built for small rows that get searched and updated. Large files bloat the database, slow down its backups and replicas, and sit on expensive fast disks for no benefit.

Store the bytes in blob storage and keep only a small row with the facts about the file and its key.

A user uploads a 2 GB video on a shaky mobile connection. How?

The client gets pre-signed URLs from the API and uploads directly to S3 using multipart upload. The file is cut into parts sent side by side.

If the connection drops, only the unfinished parts are resent. The API server never carries the video itself.

S3 reads are slow. How do you show images quickly?

Put a CDN in front of the bucket. The first request for an image is fetched from S3; after that, a copy near the user answers, which is much faster.

For data the servers themselves read constantly, keep a copy in a cache or on local disk and treat S3 as the long-term home.

How do you keep one user’s private files away from another user?

The bucket is private; nothing in it has a public address. When a user asks for a file, the API first checks in the database that this user owns it.

Only then does it create a pre-signed URL for that one key, valid for a few minutes. A leaked link stops working quickly and opens nothing else.

Two users both upload “photo.jpg”. What happens?

If the key is built from the file name, the second upload silently replaces the first.

So the key is a unique ID the server generates, and the original file name is stored in the database row. Turning on versioning adds a safety net against accidental overwrites.

What is the difference between durability and availability?

Durability is the chance the file still exists. Availability is the chance you can reach it right now.

S3’s standard class is designed for eleven nines of durability but 99.99% availability. A file can be completely safe and still be unreachable for a few minutes.

Five years of logs are costing too much to store. What do you do?

Add lifecycle rules: after a month move logs to an infrequent-access class, after a few months to an archive class, and delete them when the retention period ends.

The trade-off: archived files are cheaper to keep but slower and more expensive to read back, so this only suits data you rarely open.
